# KOBO担当

**受け持ち：** 取材で入力された言葉が、**事実として正しく、人が承認した掲載文になるまで。** KOBOの画面そのものの改修も含む。
**受け持たない：** サイトの見た目・書き出し・公開（→ `/web`）、お客様とのやり取りと取材の進め方（→ `/eigyo`）。
取材の項目を足す・削るときは、**`docs/06-取材台本.md` が仕様書**（`docs/11` 第1章「台本が仕様書」）。台本の変更は `/eigyo` と一緒に決める。

## 最初に読むもの

1. `docs/38-保留中の作業.md` の「KOBO」の節
2. 全体像 `docs/11-自社ツール設計_KOBO.md`、使い方 `tool/README.md`
3. 触る箇所の決定を `docs/04` から番号で引く（**全部は読まない**）

## よく使うコマンド（`tool/` で実行）

```
npm start                                   KOBOを開く（取材の入力画面・案件一覧）
npm run check:api                           APIキーが効くかを、いちばん小さい呼び出し1回で確かめる（D-258）
npm run webtext -- <案件ID>                 画面に出る文を欄ごとに並べる（文章は書かない）
npm run webtext -- <案件ID> --draft         AIに掲載文の下書きを書かせる（D-466。APIキーが要る）
npm run webtext -- <案件ID> --apply --by 名前   人が読んだ文を、印つきで案件データに取り込む
npm run gaps -- <案件ID> [--write]          次の取材で埋めるものを、データから出す（D-267）
npm run import:photos -- <案件ID> <フォルダ>   写真をまとめて取り込む（置き場所は人が選ぶ）
npm run generate -- <案件ID>                原稿生成（下書きは projects/<ID>/draft/。Gitに入らない）
npm run typecheck / npm test                型の検査・全部の検査
```

## APIキー（社長のご指示・いちばん先に守る）

- **APIキーが無い場合は、コードを変更して回避しない。APIキーが無いことを明記して止める。**
  「キーが無いので規則だけで作りました」のような迂回もしない。
- キーは `tool/.env` にだけ置く（`cp .env.example .env`・D-468）。`lib/env.mjs` が読み、ターミナルの値が優先する。**会話に貼っていただかない。**
- 画像生成のAPIを呼ぶコードは、まだ1行も無い（D-468・`docs/38` B-3 で社長のお答え待ち）。

## 掲載文の流れ（D-466）

```
取材の言葉（project.json の各欄）
  → AIが欄ごとに下書き（webtext --draft。下書きは draft/webtext.json）
  → 機械が検査（語尾・字数・取材に無い話題・事実の照合）
  → 人が読んで承認（--apply --by。欄ごとに reviewedAt が付く）
  → 書き出し（承認の無い欄が残っていたら公開しない）
```

- **AIの下書きは第1稿であって商品ではない**（D-013）。承認の印 `reviewedAt` はAIが書かない。人が `--apply` したときだけ付く（D-384）。
- **事実はAIに作らせない。** 数字・型番・材質・精度が取材の言葉に無ければ止める（`lib/verify.ts`・D-380。`±` の付いた `mm` も公差として照合・D-467）。
- 会社概要・対応可能範囲・設備一覧・お問い合わせは**原稿生成を通さない**。聞き取ったデータをテンプレートがそのまま出す（D-095）。
- 書く側には、社内向けの欄と「答えてもらえなかったときの発言」を渡さない（`lib/generate/writer-view.ts`・D-253）。
- 同じ文が複数の欄に入っていたら止める（D-421）。掲載文が構成の前提を壊さないようにする（D-422）。
- 「入力100%」を「書けている」と読まない。取材の言葉のまま出ている欄を、書き出しのたびに名指しする（D-419）。
- 原稿生成は Messages API で回す（D-104）。安いモデルに落とさない（D-019）。AIはビルドの途中で呼ばない（D-216）。
- AI版の Design Brief は残してあるが**当面使わない**。実案件は規則版だけ（D-266）。

## 取材の入力画面の約束

- 「未確認」マークで、聞き漏らしと「答えてもらえなかった」を区別する（D-025）。未確認の項目は隠さず、書き出しでも一覧に出す（D-094・D-135）。
- 後日確認リストと `gaps` で、次の取材に持っていくものをデータから出す。手で書き写さない（D-150・D-267）。
- 取材の最後に、お客様にその場で確認していただく画面がある（D-090）。**社内の言葉を出さない**（D-091・D-092）。
- 社内向けの欄には印（`Field.internal`）を付ける。中身がページに出たら公開を止める（D-170）。
- 見た目は取材では「どれが御社らしいですか」の1問だけ。**ご希望として記録し、決定ではない**（D-471）。
  決定は原稿のご確認で、見比べ画面の「この見た目に決める」が `themeDecidedAt` を書く（D-472）。
- ブラウザのポップアップ（`prompt`・`alert`）を使わない（D-087）。自動保存で、保存ボタンは置かない（D-077）。
- 最初の画面は案件一覧で、案件IDを1件ずつ見せる（D-469）。削除は `projects/.trash/` に移すだけ（D-084）。
- 取材の場はネットが不安定なので、**入力画面は依存パッケージなしで動く**こと（`tool/README.md`）。

## コードの約束

`tool/CLAUDE.md` にある（このフォルダのファイルを触ると自動で読まれる）。要点：
- 同じ数字や一覧を2箇所に書いたら、ずれたら落ちる検査を添える（D-197）。**型は `lib/theme.ts`・`lib/schema.ts` から読み、書き写さない。**
- 検査が赤いときは、まず測り方を疑う。緑のときも、直したものを戻して赤くなるかを確かめる。
- ブラウザで測る検査は、playwright が無ければ「未確認」と出して合格に数えない。

## KOBOと WEB制作の境目

`build-site.mjs` は WEB制作の道具だが、**掲載文の関門（承認・事実の照合・社内語）の中身はKOBOが決める。**
関門の判断を変えるときはこちらで決め、`/web` の側では関門を外さない。
