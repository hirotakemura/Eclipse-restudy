## 1. なぜ98万円に見えないのか　★実測

感想ではなく、5つの数字で言えます。

### ① 組み方の語彙が5つあるのに、1ページに1種類しか出ていない

```
定義されている layout … stack / split / offset / editorial / fullbleed（5種）
実際に出ているもの　… stack だけ（製造業・汎用とも）
```

原因は `lib/design/sections.ts` の `decorate()` です。

```ts
layout = d.layouts.find((l) => l !== "fullbleed" || a.hasRealPhotos) ?? "stack";
```

**`find` は候補の先頭を返すだけ**なので、型が `["stack","split"]` を持っていれば
広い帯は**全部 stack**、`["split","stack","offset"]` を持っていれば**全部 split** になります。
どちらにしても、**1ページの中で組み方が変わることが構造上ありません。**

ページ全体が「見出し → 中身 → 見出し → 中身」の同じ骨格で積み上がる、
という印象の直接の原因がこれです。

### ② 面（背景）が実質1色

```
定義されている surface … plain / soft / accent / grid / rule / paper / dark（7種）
製造業で出たもの　　　… plain, rule（rule は白地＋上に3pxの罫）
汎用で出たもの　　　　… plain, soft, paper（soft/paper は #f4f6f8 前後）
accent / dark / grid  … 一度も出ていない
```

`decorate()` は `pool[index % pool.length]` で候補を順に回しますが、
**型が持つ候補がほぼ白系**なので、回しても白のままです。
`accent`（アクセント地）と `dark`（白抜き）は「lead の帯に1ページ1回」という条件付きで、
**標準型・生活サービス型の候補にそもそも入っていません。**

### ③ 余白が全帯で同一

```
1440px：帯の上余白 88px（quiet の帯だけ 52.8px）
390px ：帯の上余白 40px（全帯）
```

`--section` は「雰囲気」（かたい/標準/やわらかい）で決まる**案件ごとの1つの値**で、
帯ごとには変わりません。`emphasis="quiet"` だけが 0.6倍されます。

**「疎と密を交互に置く」が、いまの仕組みでは書けません。**
余白の変化はビジュアルのリズムそのものなので、ここが一定だと、
どれだけ中身を変えても単調に見えます。

### ④ 文字の階層が、hero とその他の2段しかない

```
1440px：55 / 35 / 27 / 21 / 19 / 17(本文)
　　　　 ↑hero  ↑lead ↑h2  ↑declined ↑lead文
390px ：27 / 24 / 21 / 20 / 16(本文)
```

**55 の次が 35** で、その間がありません。hero を降りた瞬間に、
ページは「27pxの見出し＋17pxの本文」だけで最後まで進みます。

スマホではさらに潰れて、**hero 27px と h2 24px の差が3px**です。
`clamp()` の下限が「直す前のスマホの値」に合わせてあるため、
**小さい画面では見出しの階層がほぼ消えます。**

### ⑤ Visual Peak が無い

各ページで最も大きい要素は、ほぼ必ず**最初の画面**です。
本文に入ってから「ここが山」と言える場所が、構造として存在しません。

```
製造業トップ　帯の高さ 404 / 581 / 746 / 701 / 690 / 501（最大/最小 1.8倍）
```

この 1.8倍は**中身の量の差**であって、意図した強弱ではありません。

## 2. 現在の製造業 Visual Architecture

```
project.json
  ↓ analyze()            見立て（8本の筋に点数）
  ↓ resolveTheme()       顧客が選んだ9軸 → CSS変数と data-* 属性
  ↓ composeTop/Page()    帯の列を決める（content・presentation・emphasis・width）
  ↓ decorate()           面・組み方・地紋を当てる  ← ここが単調の発生源
  ↓ Band.astro           data-* を書き出すだけ
  ↓ Present.astro        content × presentation で描き分け（32組）
  ↓ site.css             属性セレクタで見た目を当てる
```

**強いところ**

- 語彙（content 11・presentation 12・surface 7・layout 5・motif 6・hero 6）は**もう揃っている**
- 可否表36組のうち32組は `Present.astro` に実装済み（残り4組も Gallery/Prose が担当）
- `data-*` が全部HTMLに出ているので、**測れる**
- 写真0枚でも建つ（D-099）

**弱いところ**

- 語彙は揃っているのに、**選び方が「候補の先頭」か「順に回す」だけ**
- 帯の内側（余白・文字サイズ）が語彙になっていない
- 地紋は今回測った2案件で**0個**（`standard` と `seikatsu` の候補が `none` のみ）

## 3. 現在の汎用 Visual Architecture

**製造業の仕組みを借りているが、借りきれていません。**

### ① 汎用でいちばん重要なページが、構成システムの外にある

`/services/`（サービス・料金）を測った結果：

```
帯（.band）の数：0　　1つの塊で 1175px
```

`pages/index.astro` の137行目にこう書いてあります。

```
{/* 汎用プランの取り扱い。**製造業には無い項目なので、構成の外に置く** */}
{isGeneral && offerings.length > 0 && (
  <Band width="normal" emphasis="normal" heading="取り扱い">
```

つまり **offerings（何を・いくらで）は content 語彙に無く**、可否表も材料条件も Brief も通りません。
幅も強さも固定です。**汎用の商品価値の中心が、デザインシステムの外**にあります。

### ② `analyze()` に汎用の分岐が無い

見立ての8本の筋は全部製造業の言葉です。

```
declined（他社が断った）／ technique ／ numbers（公差・ロット・納期）
materials（対応材質）／ equipment（設備）／ photos ／ people ／ history
```

美容室・士業・飲食で点が付くのは `photos` `people` `history` くらいで、
**残りは0点**。`primaryStrength` の語彙（precision / difficulty / speed / range /
engineering / equipment / craft / history）も同様で、**汎用の会社はほぼ `unknown` に落ちます。**

`unknown` の手順書は「特徴的な表現を割り当てず、安全な既定に任せる」（D-205）なので、
**汎用は構造的に「既定」しか出ません。**

### ③ 汎用の型が3つで、語彙の使い方が痩せている

| 型 | surfaces | layouts | motifs | heroes |
|---|---|---|---|---|
| 生活サービス | soft, plain, paper | stack, split | **none のみ** | headline, photo, type |
| 店舗・サービス | plain, soft, accent | stack, split | **none のみ** | spec, headline |
| 標準 | plain, soft | **stack のみ** | **none のみ** | headline, spec |

製造業の「精密加工」が `surfaces:[rule,grid,plain,soft] / layouts:[split,stack,offset] /
motifs:[dimension,grid,none]` を持っているのと比べると、**差は明らかです。**

**「製造業だけ高級で、汎用は簡易」という状態が、すでにコードに現れています。**

## 5. 製造業だけに必要な部分（Manufacturing Visual Language）

**会社固有の情報そのものを視覚素材にする**、はすでに方針として実装されています
（大きな数字・対比・工程・仕様表・寸法線の地紋）。歯車や工場アイコンは1つも入れていません。

足すべきもの：

- **Spec Wall**：条件表を「表」ではなく画面を占める構成物として見せる
- **Number Peak**：`±0.005mm` を1画面に1つだけ、巨大に置く（いまは `bignumber` 52px 上限）
- **Process Peak**：課題→工程→結果を、カードではなく縦の大きな流れとして見せる
- **Equipment Wall**：型番の一覧を、カード格子ではなく整列した壁として見せる
- **Drawing Grid**：方眼の面（`grid`）を、いま一度も出ていないので実際に効かせる

## 6. 汎用だけに必要な部分（General Visual Language）

- **Offering**：content 語彙に `offerings` を足す（最優先。いまシステムの外）
- **Brand Statement**：会社の一言を、写真なしで画面の山にする
- **Staff / People**：人を主役にする構成
- **Editorial Lead**：大きな見出し＋余白で、情報量の少なさを弱点にしない
- **Menu / Price**：料金表を「表」ではなく読み物として見せる
- 見立ての筋を**汎用用に別に定義する**（`analyze()` の分岐）

## 8. Visual Composition 層をどこに置くか

**新しい層を1つ、`decorate()` と `Band.astro` の間に入れます。**

```
composeTop/Page()      … 何を・どの順で（いまのまま）
  ↓ Section[]
【新】composeVisual()   … リズム・山・余白・文字・面・組み方を、ページ単位で決める
  ↓ VisualSection[]
Band.astro             … data-* を書き出す（属性が増えるだけ）
site.css               … 属性セレクタを足す
```

**なぜ `decorate()` の中でやらないか。**
`decorate()` は帯を1つずつ見るので、**ページ全体のリズムを決められません。**
「山を1つ作る」「密のあとに疎を置く」は、列全体を見ないと書けない判断です。

`composeVisual()` が決めるもの（すべて既存の語彙＋新語彙のIDのみ。CSSは書かせません）：

```
peak        … この帯が山か（1ページ1つ）
density     … tight / normal / loose / vast（上下余白）
titleScale  … display / large / normal / small（見出しの大きさ）
surface     … いまの7種（選び方を「型の候補を順に回す」から変える）
layout      … いまの5種（同上）
media       … full / inset / none
```

## 10. Design Brief との接続

Brief の形（`DesignBrief`）に、**語彙のIDだけ**を足します。

```ts
interface DesignBrief {
  primaryStrength; secondaryStrength; hero; blocks; motif; motionLevel;   // いまのまま
  peak?: ContentId;          // どの帯を山にするか
  cta?: CtaId;               // 問い合わせ導線の型
  rhythm?: DensityId[];      // 帯ごとの余白（blocks と同じ長さ）
}
```

`BriefBlock` に `density?` `titleScale?` を足します（`surface` `layout` `media` は既にあります）。

**検査は6段になります**：形 → 語彙 → 可否 → 材料 → 情報量（D-259）→ **リズム**。
リズムの段では「山が2つ以上ないか」「全帯が同じ余白になっていないか」を見ます。

**AIにHTML/CSSは書かせません。** 既存方針（D-200）のとおり、返させるのはIDだけです。

## 13. 既存コードへの影響とリスク

| 変更 | 影響範囲 | リスク |
|---|---|---|
| `composeVisual()` を足す | `build-site.mjs` と `brief-rules.ts` の呼び出し2箇所 | 低。既存の `Section[]` に属性が増えるだけ |
| `Band.astro` に属性追加 | 全帯 | 低。未指定なら既定値 |
| `site.css` に属性セレクタ追加 | **全ページのHTML**（CSSはインライン化されるため） | **中。3社の基準HTMLが全部変わる** |
| content 語彙に3つ追加 | 可否表・材料条件・`Present.astro`・Brief検査 | 中。**可否表を通さない content があると4段検査が落ちる**（D-262で踏んだ穴） |
| 汎用の型を6つ追加 | `direction.ts`・顧客の選択画面 | 中。**既存の3型を消さない**（D-198） |
| `analyze()` に汎用の分岐 | 見立て全体 | **高。製造業の見立てを1点も動かさないこと**（基準HTMLで検出可能） |
| Typography スケール | `site.css` の見出し全部 | **高。全ページの見た目が変わる** |

**いちばん大きなリスク**は、CSSがインライン化されるため、
**どんな小さなCSS変更でも全ページのハッシュが変わる**ことです（D-236）。
基準（`baseline-ai-off.json`）は**Phaseごとに1回だけ、最後に取り直します。**

**2番目のリスク**は、**実案件がまだ1件も無いこと**です。逆に言えば、
**いま壊しても壊れるのは架空の案件だけ**なので、着手するなら今です。

## 15. AIを使うべき部分／規則で十分な部分

D-264・D-265 で実測した結論をそのまま当てはめます。

| 判断 | どちらか | 根拠 |
|---|---|---|
| 帯の並び順 | **規則** | 3社ともAIが同じ動きを返した。会社ごとの判断ではなかった（D-264） |
| 表現（presentation）の選択 | **規則** | AIに触らせると情報が減る方向に動く（D-259・5/5件） |
| 余白・文字の大きさ・面・組み方 | **規則** | 「密のあとに疎」はページ全体の形の話で、会社ごとの判断ではない |
| **どの帯を山にするか** | **AIの候補** | ここは会社ごとに変わる。ただし**規則版が先に決め、AIは入れ替えを提案するだけ** |
| **CTAの型** | 規則（当面） | 材料（写真の有無・業種）から決まる |
| Design Direction の推薦 | AIの候補 | いまは顧客が選ぶ。将来、取材データから推薦してもよい |

**AIを入れるのは Phase 9 です。** 規則版で作りきってから、
「規則では書けない判断」が残っているかを測ります。**残っていなければ入れません**（D-266）。

## この文書の結論
