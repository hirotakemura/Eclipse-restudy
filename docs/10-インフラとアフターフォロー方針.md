# インフラ方針・アフターフォロー設計

作成: 2026-09-12 / 状態: **アドバイザー承認待ち（技術方針の転換を含む）**

---

## 1. 【重要】技術スタックの方針転換：WordPress → 静的サイト

`02-サービス設計_v0.md` で「WordPressを採用する」と決定したが、**これを撤回する。**

### 撤回する理由

自社ツールでサイトを自動生成する設計を詰めた結果、WordPressでは事業が成立しないことが分かった。

**理由1：保守工数が事業を殺す**

WordPressは月次の保守が必ず発生する。本体更新、プラグイン更新、PHPバージョン対応、脆弱性対応、改ざん監視。
1サイトあたり月30分としても、**10サイト抱えた時点で月5時間。** 週15時間の体制でこれは致命的。しかもこの工数は売上に比例して増えるのに、単価は増えない。**保守契約の粗利が、サイト数に応じて逆に下がっていく構造**になる。

**理由2：ランニングコストがサイト数に比例する**

レンタルサーバー月1,000円 × サイト数。10サイトで月1万円。静的サイトならゼロ。

**理由3：自動生成との相性が悪い**

DB・テーマ・プラグインの状態を持つWordPressを外部から自動生成するのは、技術的には可能だが壊れやすい。生成ツールの保守自体が負債になる。

**理由4：表示速度で差がつけられない**

提案書（`07`）で「表示速度が遅い」を競合の弱点として指摘する設計にした。自分たちがWordPressだと、この指摘の説得力が落ちる。

### 代わりに採用するもの

| レイヤー | 採用 |
|---|---|
| サイト生成 | **Astro**（静的サイトジェネレータ） |
| ホスティング | **Cloudflare Pages** |
| フォーム | Cloudflare Pages Functions + Resend（メール送信） |
| スパム対策 | Cloudflare Turnstile |
| 解析 | Google Analytics 4 + Search Console |
| コンテンツの正 | **自社ツール（KOBO）のプロジェクトデータ** |

### 1サイトあたりの原価

| 項目 | 月額 |
|---|---|
| Cloudflare Pages | 0円（無料枠で十分） |
| Resend（フォームのメール送信） | 0円（月3,000通まで無料） |
| Turnstile | 0円 |
| ドメイン | 年1,500円 ※**顧客名義・顧客負担** |
| **合計** | **実質 0円** |

> **これが効く。** 月5万の保守契約の粗利がほぼ100%になり、サイト数が増えてもコストが増えない。
> WordPressなら10サイトで月1万円のサーバー代＋月5時間の保守工数。**同じ売上で、利益も時間も残らない。**

### 仕組みの違い（判断の前提）

```
WordPress ── 訪問のたびに組み立てる
  訪問者 → サーバー → PHPが動く → DBに問い合わせ → HTML組み立て → 返す
                       ↑ これを訪問のたびに毎回

Astro ── 先に作って置いておく
  【公開時に1回だけ】原稿 → ビルド → 完成したHTMLファイル
  【訪問のたび】    訪問者 → CDN → ファイルを返すだけ
```

製造業の言葉でいえば **受注生産（WordPress）と、見込み生産＋在庫出荷（Astro）** の違い。
この一点から、速度・障害・セキュリティ・保守工数・原価の差がすべて派生する。

| | WordPress | Astro（静的） |
|---|---|---|
| 表示速度 | 組み立てに時間がかかる | ファイルを返すだけ。桁違いに速い |
| 障害 | サーバー・PHP・DBのどれが詰まっても落ちる | 落ちる要素がほぼない |
| セキュリティ | サーバー上で動くプログラムがある＝攻撃対象。侵入経路の大半はプラグイン | 実行されるプログラムが無く、改ざんの経路がほぼない |
| 月次保守 | 本体・プラグイン・PHPの更新が毎月発生 | ほぼ不要 |
| 月額原価 | サーバー代 約1,000円/サイト | 0円 |

### この判断のデメリット（正直な記録）

**一方の主張しか書かれていない意思決定の記録は、後から検証できない。** 弱点を明記しておく。

**① 顧客が自分で更新できない**

WordPressは管理画面から誰でも書ける。Astroはビルドと公開の手順が要る。
→ **承知の上で捨てる。** 中小製造業で実際にWordPressの更新を続ける会社は1割に満たず、
使われない機能のために保守コストを払い続けることになるため（D-010）。

**② 動的な機能が必要な案件には向かない**

会員制・予約システム・EC・サイト内検索・コメント。これらはWordPressのほうが早い。
→ いずれも `02-サービス設計_v0.md` 第5章「やらないこと」に含まれるため、現時点では問題にならない。
**この前提が崩れたら（EC案件を受けると決めたら）、この判断も見直す。**

**③ 引き継げる会社が少ない ★最も重いデメリット**

WordPressは世界中の制作会社が扱える。Astroを扱える会社は、特に北九州では少ないと見るべき。
**提案書（`07`）で「他社に乗り換えられます」と約束している以上、これは軽く扱えない。**

ただし、見た目ほど深刻ではない：
- 成果物は素のHTML/CSSであり、**どの制作会社でも引き取れ、どのサーバーにも置ける**
- むしろ他社が作り込んだWordPressのカスタムテーマのほうが引き継ぎは厄介
- 引き継げないのは「更新の仕組み」であって「サイト」ではない

→ **対応：契約終了時にHTML一式＋原稿テキスト＋画像原本を無償で引き渡す。契約書に明記する**（第4章）。
これなら次の業者がWordPressで作り直すにしても、ゼロからにはならない。

### 判断の分かれ目

> **サイトを「作って売る」事業なら WordPress でよい。**
> **保守契約を「積み上げる」事業なら、保守工数がゼロに近いほうが勝つ。**

我々はKGIをMRRに置いた（`01` 第3章）。**サイト数が増えるほど利益が出る構造にしなければ事業が成立しない。**
WordPressはその逆で、増えるほど時間と金を食う。だから撤回する。

### 顧客への説明（技術用語を使わない）

> 「一般的なホームページは、見られるたびにサーバーの中でページを組み立てています。
> うちは先に完成させたものをお渡しする方式なので、表示が速く、止まりません。
>
> それと、よくあるホームページは毎月プログラムの更新作業が必要で、放置すると乗っ取られることがあります。
> うちの方式には、その作業自体がありません。」

**「止まらない」「乗っ取られない」。工場を止められない人たちには、この2つが刺さる。**

### 「顧客が自分で更新できる」という当初の論拠について

WordPressを選んだ理由は「顧客が自分で更新できるから」だった。これは**実態に合っていない。**

中小製造業にWordPressを渡して、実際に更新を続ける会社は体感で1割に満たない。「更新できます」は売り文句としては効くが、使われない機能に保守コストを払い続けることになる。

方針を変える：

> **更新は保守契約に含めて我々が代行する（ベーシックで月2回まで）。**
> これは顧客にとってもラクで、我々にとっては保守契約の価値の裏付けになる。

### 「乗り換え自由」の約束はどう守るか

提案書（`07`）で「他社に乗り換えられます」と明記している。ここは絶対に守る。

| 項目 | 担保の方法 |
|---|---|
| ドメイン | **顧客名義で取得する。** 手続きは代行するが、名義と支払いは顧客 |
| 原稿・画像 | いつでもエクスポートして引き渡す（テキスト＋元画像） |
| サイトのソース | 生成済みHTML/CSS一式を引き渡す。静的なのでどこにでも置ける |
| 契約終了時 | 上記を無償で引き渡す。**契約書に明記する** |

**ドメインを顧客名義にするのは、ロックインしないという約束の核心であり、同時に我々がドメイン更新忘れの責任を負わないためでもある。**

### 例外：顧客がWordPressを指定してきた場合

社内にWP経験者がいる、前の業者がWPだった、といったケースは実際に起きる。

> **対応はする。ただし運用契約に月額2万円を上乗せする。**

保守工数が実際に増えるため。この価格差が、自然に静的サイトへの誘導になる。

## 2. ドメインとDNSの実務

| 項目 | 方針 |
|---|---|
| レジストラ | お名前.com / ムームードメイン（顧客名義） |
| 取得手続き | **我々が代行**（画面共有しながら顧客に操作してもらう or 委任状ベースで代行） |
| 支払い | 顧客のカード。自動更新をONにする |
| DNS | Cloudflare に移管（ネームサーバー変更）。**ここは我々が管理** |
| 既存サイトからの移行 | 切替前に新サイトをプレビューURLで確認 → DNS切替は平日午前に実施 |

> **ドメイン更新切れは、この事業で起こりうる最悪の事故。** サイトが消え、メールも止まる。
> 自動更新の設定を必ず確認し、**ツール側で全案件の有効期限を管理して60日前に通知する。**

## 3. アフターフォロー設計

### 3-1. プラン別の提供内容（`02-サービス設計_v0.md` の改訂）

| | ベーシック 月5万 | グロース 月10万 | フル 月15万 |
|---|---|---|---|
| 更新対応 | 月2回まで | 月4回まで | 無制限（常識の範囲） |
| 障害対応 | ○ | ○ | ○ |
| ドメイン/SSL期限管理 | ○ | ○ | ○ |
| フォーム疎通監視 | ○ | ○ | ○ |
| 月次レポート | 自動生成 | 自動生成＋所見 | 自動生成＋所見 |
| 技術記事の執筆 | — | 月1本 | 月2本 |
| 改善提案 | — | 四半期1回 | 月1回 |
| 定例ミーティング | — | — | 月1回（30分） |
| 広告運用 | — | — | ○（広告費別） |

### 3-2. 自動化するもの（人間の時間を使わない）

静的サイトは障害がほぼ起きない。**アフターフォローの工数は「自動化できるか」で決まる。**

| 項目 | 頻度 | 実装 |
|---|---|---|
| **フォーム疎通テスト** | 週1 | 自動送信 → 受信確認。失敗したら即通知 |
| ドメイン有効期限チェック | 日次 | 60日前・30日前・7日前に通知 |
| SSL証明書チェック | 日次 | Cloudflareが自動更新するが監視はする |
| サイト死活監視 | 5分ごと | UptimeRobot（無料枠） |
| 月次レポート生成 | 月1 | GA4 + Search Console API から自動生成してPDF化 |

> **フォームの疎通監視は絶対に外さない。** 問い合わせが実は届いていなかった、というのは顧客にとって最悪の裏切りであり、我々が即座に信用を失う唯一の事故。

### 3-3. 月次レポートの中身

製造業の社長が見て意味が分かるものにする。セッション数だけ並べても読まれない。

```
■ 今月の問い合わせ　　　　　　　  {{n}}件（先月比 {{±n}}件）
　　内訳：新規取引の相談 {{n}}件 ／ 見積依頼 {{n}}件 ／ 採用応募 {{n}}件

■ 検索で見られた回数　　　　　　  {{n}}回
　　流入が多かった検索語
　　　1. {{キーワード}}　　{{n}}回（順位 {{n}}位）
　　　2. ...

■ よく読まれたページ
　　　1. 加工事例：{{タイトル}}　　{{n}}回

■ 今月の作業
　　　・{{更新内容}}

■ 来月のご提案
　　　{{1つだけ。多いと読まれない}}
```

**「今月の問い合わせ件数」を一番上に置く。** 保守費を払い続ける理由がここにしかないため。

### 3-4. 更新依頼の受け口

- 専用のメールアドレス（update@{{ドメイン}}）で受ける
- **電話での依頼も受ける。** 製造業の社長はメールを書かない。電話を嫌がると更新が止まり、サイトが死ぬ
- 受けたら**48時間以内に反映**（軽微なもの）。これをSLAとして明記する

> 更新のハードルを下げることが、解約防止の最大の施策。**「頼みづらくて放置」が解約の典型パターン。**

## 4. 解約時の手順（先に決めておく）

揉めるのは必ず解約時。先に決めて契約書に書く。

1. 解約は**1ヶ月前の申し出**で成立
2. サイトのソース一式（HTML/CSS/JS/画像）と原稿テキストを**無償で引き渡す**
3. ドメインは顧客名義なので何もしない。DNSの管理権限を顧客または次の業者に移す
4. **引き渡し後、こちらのCloudflareアカウントからは削除する**
5. 違約金は取らない

> **気持ちよく辞められるようにしておく。** 中小製造業は横の繋がりが強く、揉めた話は必ず広まる。逆に、円満に辞めた顧客が次の顧客を紹介してくることも実際にある。
