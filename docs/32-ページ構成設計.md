# 第6段階 設計案 — 会社固有型サイト構成（Company-driven Page Architecture）

**これは設計案である。コードはまだ1行も変えていない。**
アドバイザーのレビューを受けてから実装に入る（第0段階と同じ手順）。

---

## 0. 結論から

**新しい層を足す話ではない。** KOBOには既に「会社の勝ち筋」を持った表がある
（`PLAYBOOK`・`analysis.primaryStrength`）。**それがページの中にしか届いていない**のが問題である。

```
いま                          あるべき
──────────────────────────    ──────────────────────────
Analysis（会社の勝ち筋）       Analysis（会社の勝ち筋）
  ↓ ここで止まっている           ↓
  │                          【新】Architecture  どのページを・どの順で・どれだけ厚く
  ↓                            ↓
site.ts の手書き配列 ←★       composePage（depth を受け取る）
  ↓                            ↓
composePage                  composeVisual
  ↓                            ↓
composeVisual                composeAssets
  ↓
composeAssets
```

★が唯一「会社を見ていない層」である。その下の層は、もう全部会社を見ている。
**上流から変えるべきは `site-template/src/lib/site.ts` の `nav` 配列である。**

## 1. 現在のページ構成決定ロジック（実測）

ページ集合は**3箇所**に手書きされている。

| 場所 | 何を決めているか |
|---|---|
| `site-template/src/lib/site.ts` の `nav` | ページの**集合と順番**（手書きの配列） |
| 各 `.astro` の `getStaticPaths()` | そのページを**作るかどうか** |
| `lib/design/assets.ts` の `photoRequestsFor` | 写真の依頼を集めるための**ページ表**（書き写し） |

3つがずれないよう `asset.test.mjs` が突き合わせている（D-197 の形）。
**表を3つ持っていること自体が、この段階で解消すべき負債である。**

条件は `formSet`（商品）と、データの有無だけ。

```
製造業（980,000円）  index → capability → equipment → strengths → cases
                     → company → recruit → message → contact   （9ページ固定）
汎用（198,000円）    index → services → strengths → cases → company → contact（6ページ固定）
```

`cases` / `recruit` / `message` / `services` だけがデータの有無で出入りする。
**順番は1社たりとも変わらない。**

## 2. 実測：7社を並べた結果

| 会社 | 強み | ページ | トップの帯 | 各ページの帯数 |
|---|---|---|---|---|
| A 精度 | precision | 9（同一） | hero→figures→cases→technique→materials→equipment | 3/3/3/2/3/3/2/2 |
| B 難加工 | difficulty | 9（同一） | hero→**declined**→cases→technique→figures→materials | 4/3/2/3/3/3/2/3 |
| C 短納期 | speed | 9（同一） | hero→figures→cases→technique→**equipment**→materials | 3/3/3/2/3/3/2/2 |
| 松原精機 | difficulty | 9（同一） | Bと同じ | Bと同じ |
| 汎用A | record | 6（同一） | hero→offerings→cases→technique→declined | — |
| 汎用B | reason | 6（同一） | hero→**declined**→cases→technique→offerings→points | — |
| 汎用C | person | 6（同一） | hero→offerings→cases→technique→**points**→declined | — |

読み取れること。

1. **トップページだけは、もう会社ごとに違う。** ここは既に成功している
2. **ページの集合・順番は、商品が同じなら完全に同一**
3. **厚みの幅が無い。** どのページも2〜4本で、A（精度）とC（短納期）は**帯数が完全に一致**
4. 事例ページ2〜3本・問い合わせ2〜3本。**いちばん厚くしたいページが、いちばん薄い**

## 3. Analysis から使える会社固有情報

すでに揃っている。**新しく取材する必要はない。**

| 値 | 中身 | 構成に使えるか |
|---|---|---|
| `primaryStrength` | 15種（precision / difficulty / speed / range / engineering / equipment / craft / offering / price / reason / voice / record / person / history / unknown） | ◎ **順序と厚みの主軸** |
| `secondaryStrength` | 同上。根拠が2つあるときだけ | ○ 2番目に厚くするページ |
| `strands[]` | 何で見せる会社か（10種）＋点数＋理由 | ◎ **厚みの配分** |
| `figures[]` | 大きく出す価値のある数字 | ○ 条件ページの厚み |
| `seeking` / `avoiding` / `profitable` | もっと受けたい／減らしたい／利益率の高い仕事 | ◎ **まだ一度も構成に使っていない** |
| `hasRealPhotos` | 実写の有無 | △ 構成には使わない（D-286） |
| `inquiry.goals` | 集客／選別／採用／信用構築 | ◎ **サイトの目的そのもの。いまは採用ページの有無にしか使っていない** |

**いちばん惜しいのは `goals` と `seeking` / `avoiding` である。**
「選別」が目的の会社と「集客」が目的の会社で、同じ順番のサイトを出している。

## 4. 15方向とページ構成の関係

**いまは関係が無い。** `direction`（型）は面・地紋・余白・素材にしか効かない。

そして**それで正しい**と考える。型は「見た目の好み」であって、
「何から読ませるか」は会社の勝ち筋で決まるべきものである（D-282 で型の重みを ±2 に下げたのと同じ理由）。
**第6段階でも、型にページ構成を触らせない。**

## 5. 必須ページと可変ページ

| 分類 | ページ | 理由 |
|---|---|---|
| **絶対必須** | `index` / `company` / `contact` | 会社の実在確認・連絡先。**落とすと商品として成立しない** |
| **実質必須**（製造業） | `capability` / `equipment` | **SEOの本体。** 材質・加工法・メーカー・型番が、そのまま検索語になる |
| **条件付き** | `cases` / `cases/N` | 事例があるとき |
| **条件付き** | `recruit` | 目的に「採用」があり、募集要項があるとき |
| **条件付き** | `message` | 目的に「採用」か「信用構築」があり、代表の言葉があるとき |
| **条件付き**（汎用） | `services` | 取り扱いがあるとき |
| **強みで可変**（新設候補） | `flow`（相談から納品までの流れ） | 短納期・対応力で選ばれる会社 |
| **強みで可変**（新設候補） | `people`（働く人・考え方） | 職人・人で選ばれる会社 |

**新設は2枚まで。** ページを増やすこと自体は目的ではない。
「その会社の勝ち筋を説明するのに、既存のページでは器が足りない」ときだけ足す。

## 6. 提案するデータ構造

```ts
/** そのページが読む人に何を渡すか。**順序を決める軸になる** */
export type PageRole =
  | "entry"     // 入口（index）
  | "proof"     // 証拠（cases・case/N）
  | "capacity"  // 受けられるか（capability・equipment・flow）
  | "trust"     // 会社の信用（company・message・history）
  | "people"    // 人（recruit・people）
  | "action";   // 行動（contact）

export interface PageSpec {
  slug: PageSlug;
  /** 出すか。**落とした理由も残す** */
  presence: "required" | "included" | "dropped";
  /** 0〜100。メニューの順・内部リンクの重み・sitemap の priority に使う */
  priority: number;
  /** 何本の帯まで許すか。1〜4。**材料が無ければ埋まらない** */
  depth: 1 | 2 | 3 | 4;
  role: PageRole;
  /** なぜそうなったか。**社長に説明できない構成は出さない** */
  why: string;
}

export interface SitePlan {
  pages: PageSpec[];          // priority の高い順
  /** どの勝ち筋で組んだか。`explain()` と `npm run gaps` に出す */
  strength: PrimaryStrength;
  why: string;
}

export function composeSite(
  project: Project,
  a: Analysis,
  /** **型は受け取らない**（§4）。ページ構成は見た目の好みで変えない */
): SitePlan;
```

**`brief` を引数に取らない。** Asset層と同じ設計で、AI Brief がこの先どう確定しても
ページ構成は影響を受けない（D-304 と同じ）。

## 7. 提案するルール

### Presence

```
required   index / company / contact           …… 常に
required   capability / equipment（製造業）     …… 常に（SEOの本体）
included   cases / case/N / recruit / message / services …… 材料があるとき（現状どおり）
included   flow    …… primaryStrength が speed / range、かつ工程の聞き取りがあるとき
included   people  …… primaryStrength が craft / person、かつ働く人の記述があるとき
dropped    それ以外
```

**「落とす」判断は作らない。** 材料が無ければ最初から候補に挙がらないだけである。
AIにページを落とさせない（落とした理由を後から説明できないため）。

### Priority（順序）

`PLAYBOOK` と同じ形の表を1枚足す。**入口と行動は固定、中間だけ並べ替える。**

```ts
const ARCHITECTURE: Record<PrimaryStrength, PageRole[]> = {
  precision:   ["entry", "capacity", "proof", "trust", "people", "action"],
  difficulty:  ["entry", "proof", "capacity", "trust", "people", "action"],
  speed:       ["entry", "capacity", "proof", "trust", "people", "action"],
  equipment:   ["entry", "capacity", "proof", "trust", "people", "action"],
  craft:       ["entry", "people", "proof", "trust", "capacity", "action"],
  person:      ["entry", "people", "trust", "proof", "capacity", "action"],
  …
  unknown:     ["entry", "capacity", "proof", "trust", "people", "action"], // 現状と同じ
};
```

- `entry` は必ず先頭、`action` は必ず末尾（**変えると使い勝手が壊れる**）
- 同じ役割の中の順番は、現在の並び（`capability → equipment`）を維持する
- `unknown` は**現在とまったく同じ並び**にする。根拠が無いのに並べ替えない（D-205）

### Depth（厚み）

```ts
/** 勝ち筋のページを1本厚く、それ以外は現状どおり */
depth = base[slug] + (thisPageCarriesTheStrength ? 1 : 0)
```

**厚くする＝新しい内容を作る、ではない。**
いまトップページに出ている帯を、そのページにも降ろす／1本の帯を2本に割る、のどちらかだけ。
材料が無ければ `composePage` が何も足さないので、**水増しにならない。**

| 勝ち筋 | 厚くするページ | 何を厚くするか（材料はすべて既存） |
|---|---|---|
| difficulty | `cases` | 課題 → 対応 → 結果 → 技術（いま2〜3本 → 4本） |
| equipment | `equipment` | 主な設備 → 一覧 → 生産体制（台数・人員・稼働） |
| speed | `flow` | 相談 → 対応 → 生産 → 納品 |
| craft / person | `people` | 人物 → 仕事 → 会社の考え方 |
| precision | `capability` | 条件 → 材質 → 仕様 → 検査（検査の記述があるとき） |

## 8. A/B/C の期待結果

| | A 精度 | B 難加工 | C 短納期 |
|---|---|---|---|
| メニュー順 | トップ → **対応可能範囲 → 設備一覧** → 強み・技術 → 加工事例 → 会社概要 → 採用 → 挨拶 → お問い合わせ | トップ → **加工事例 → 強み・技術** → 対応可能範囲 → 設備一覧 → 会社概要 → … | トップ → **対応の流れ → 対応可能範囲** → 設備一覧 → 加工事例 → … |
| 厚くなるページ | `capability`（3→4本） | `cases`（2→4本） | `flow`（新設・4本） |
| ページ数 | 9（変わらず） | 9（変わらず） | **10**（`flow` を足す） |
| 落ちるページ | 無し | 無し | 無し |
| URL | すべて現状と同じ | すべて現状と同じ | `flow` のみ新規 |

**ページ数はほとんど変わらない。変わるのは順番と厚み**である。
「会社ごとに違うサイト」を、ページ数の増減ではなく**読ませる順**で作る。

## 9. SEO を壊さない条件

1. **URL を強みで変えない。** `slug` は固定。順序が変わってもURLは同じ
   （同じ会社を再生成したときにURLが動くのが、いちばん危ない）
2. **必須ページを落とさない**（§5）。製造業の `capability` / `equipment` は検索語の本体
3. **`sitemap.xml` と `robots.txt` を作る。** 実測で**どちらも存在しない。**
   順序の意図を検索エンジンに伝えられるのはここだけなので、`PageSpec.priority` から生成する
4. **`title` / `description` を会社固有にする。** いまは全社が同じ雛形
   （`${会社名}の${ページ名}`）で、**これ自体が「汎用サイトに見える」原因**である。
   `PageRole` と勝ち筋から作る
5. **一度公開したページ集合を `project.json` に記録する。**
   再生成でページが減ると、公開後はリンク切れになる。**減る変更は書き出しで警告**にする
   （`build-site.mjs` の公開判定に1項目足す）

## 10. 再現性

`composeSite(project, analysis)` は**純関数**にする。乱数・時刻・ネットワークを使わない。

- 同じ `project.json` → 同じ `SitePlan`（試験で2回組んで突き合わせる）
- AI を使わない（§11）ので、**生成のたびに構成が変わることがない**
- `why` を全ページに持たせ、`npm run gaps` と `explain()` に出す。
  **社長が「なぜこの順番か」を説明できない構成は出さない**

## 11. ルールだけで十分か、AI Brief を使うべきか

**使わない。** 理由は3つ。

1. **ページ構成は一度決めたら動かしにくい。** URLと検索順位が乗るので、
   生成のたびに揺れてよい種類の判断ではない
2. **AIが落としたページは、落とした理由を後から説明できない。**
   「このページが無いのはなぜか」に答えられない商品は売れない
3. AI Brief は当面使わないと決めてある（D-266）

ただし**穴だけ空けておく**。`secondaryStrength` があるときの
「2番手をどこまで厚くするか」は、将来AIに任せられる唯一の余地である。
いまは規則で「2番手は厚くしない」と決めておき、`composeSite` の引数に `brief` を**書かない**
（引数に無ければ、AI Brief がどう確定してもこの層は影響を受けない・D-304）。

## 14. 移行方法（3段階）

**第1段階（無変更の証明）**
`composeSite` を作るが、返す並びは**現在の `nav` と完全に同じ**にする。
`site.ts` / `getStaticPaths` / `photoRequestsFor` をそこから生成し、
**書き出したHTMLがバイト単位で一致すること**を確かめる。
ここで**表を3つ持っている負債が消える。**

**第2段階（順序）**
`ARCHITECTURE` の表を入れる。`unknown` は現状の並びのままにしておく。
`sitemap.xml` / `robots.txt` / 会社固有の `title` を同時に入れる。
A/B/C の順序が違うことを画面で確かめる。

**第3段階（厚みと新設ページ）**
`depth` を `composePage` に渡す。`flow` / `people` は**必要だと分かってから**作る。

## 15. 正直な見立て

第5段階の総括で挙げた「デザイン品質を上げる次の最重要ポイント」は、優先順に

1. 写真を1枚でも入れる導線
2. **ページ構成そのものを会社で変える** ← 第6段階はここ
3. 余白とタイポグラフィの段を深くする

だった。**第6段階は2番目に手を付けることになる。**

1番（写真）は**我々のコードでは解決できない**（お客様から預かるもの）ので、順番として妥当だと考える。
ただし、**「安っぽく見える」の8割は写真の不在である**という見立ては変わっていない。
ページ構成を会社ごとに変えても、**写真0枚のサイトが上質に見えるようにはならない。**

3番（余白・タイポ）は**今日のコードだけで動かせて、全ページに効く**。
第6段階と並行して進めるか、先に済ませるかは、ご判断をいただきたい。
