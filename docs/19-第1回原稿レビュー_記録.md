# 第1回レビュー（実施記録）

実施日：2026-09-13　実施者：アドバイザー　閲覧：`preview:site` で全ページ

**前提**：`npm run generate` の機械判定は未実施。**書き出されたサイトを顧客の目で読む**形で行った。
原稿生成を通さない経路（データ直描き）のレビューであり、これは想定外ではなく**本番と同じ経路**である。

## 指摘の要旨

1. **設備一覧に社内の作業メモが出ていた。** 「ABC123」という仮の型番と、
   「型番は社長の口頭記憶のため、現地で銘板と照合して確定させること」がメーカー欄に出力されていた
2. **強み・技術の文末**に「具体的な数値は工場長に要確認。」が出ていた
3. 事例2〜4の情報が薄く、**4件分の取材が実質1.3件分**しか終わっていないように見える
4. **採用ページが求人として成立していない**（労働条件がほぼ空欄）
5. **写真が実質ゼロ**（仮のSVGのみ）。「治具を自社で作る」という強みは写真でしか伝わらない
6. **お問い合わせに入力フォームがない**（メールアドレスの記載のみ）。図面添付が要る業種で機会損失
7. 同じ説明文（治具・薄物）が複数ページで繰り返され、独自情報の薄いページがある
8. 総合判定：**「手直しなしで70%使える」には届いていない**

## 社長側での再現と確認（2026-09-13）

**1・2・4・5・6 は再現した。7 も確認した。**
このサイトは書き出し時に**「公開してよい状態です」と判定されていた。** ここが最も重い。

再現の過程で、指摘されていない同種の欠陥をもう1件見つけた：

- **採用ページに社内事情が出ていた。**
  「若手の定着はどうですか」（＝採用ページを作るべきかを判断するための質問）の答えが、
  「定着の状況」という見出しでそのまま公開されていた。本文は
  **「人手が足りず受注を絞らざるを得ない状態」。** 求職者にも見込み客にも見せる話ではない
- 代表挨拶の末尾が「社長自身も本取材で気づかされた、**と述べている**」。取材メモの地の文のまま
- 強み・技術の見出しが「**取材で詳しくうかがった点**」。制作の都合が見出しになっていた

一方、**再現しなかった**もの（アドバイザーの環境と当方のデータが異なるため）：

- `{{要確認：採用ページURL}}` のような**サイト内リンクの未解決**。当方の書き出しには出ていない。
  ただし指摘の筋（サイト内の既存ページは生成側が自動で埋めるべきで、
  本当に確認が要る項目と混ぜてはいけない）は正しいので、`prompts.ts` の課題として残す
- 「写真が一枚もない」は正確には「**仮のSVGが9枚あり、実写がゼロ**」。
  枚数の上では埋まって見えていたことが、むしろ問題だった

## 根本原因（1つ）

**KOBOの項目には「お客様に出す欄」と「我々が判断するための欄」が混ざっている。**
テンプレートはその区別を持っていないので、**社内の欄がそのまま顧客のページになる。**

安全装置（`lib/verify.ts`）は「**生成原稿が案件データから外れていないか**」しか見ていない。
検証の向きが一方向で、**案件データそのものが顧客に出せる文章か**は誰も見ていなかった。
「ABC123」は案件データに書いてあるので、出典照合では「出典あり」として通ってしまう。

## 直したもの（D-169〜D-174）

| 指摘 | 直した場所 |
|---|---|
| 社内の作業メモがページに出る | `tool/lib/internal-language.ts`（新規）＋公開前の検査。**言葉のほうを見る** |
| 社内向けの欄が公開される | `Field.internal` を新設し、その中身がHTMLに出たら公開を止める |
| 仮の画像のまま公開できてしまう | 仮のSVGが残っていたら公開不可にした |
| 採用ページが求人として成立しない | 「募集要項」ブロックを新設（労働条件11項目） |
| 事例の情報が薄い | 事例1件ごとに 数量・ロット／納期／他社が断った理由 を追加し、表で出す |
| 電話番号が必須になっていなかった | `required` を付けた。受付時間の欄も追加 |
