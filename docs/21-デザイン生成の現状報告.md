## 1. 現在のデザイン生成フロー

実際には**2本の独立した流れ**があり、合流するのは最後のAstroビルドだけです。

```
【A】文章の流れ（Claude を通る）
  project.json ─→ decidePages() ─→ ページごとに Claude ─→ verifyDraft() ─→ draft/*.md
                  （pages.ts）      （pipeline.ts）        （verify.ts）

【B】構造とデータの流れ（Claude を通らない）
  project.json ───────────────────────────────────→ Astro の .astro が直接描画
                                                     （表・一覧・カード・ナビ）

【C】見た目の流れ
  project.json の theme ─→ resolveTheme() ─→ CSS変数 + <html data-*>
```

### ここが要点

- **【B】は Claude を通りません**（D-095）。表と一覧に創作は要らない、という判断です。
  したがって**構造を決めているのは .astro のコードそのもの**で、会社情報ではありません。
- 【A】が生成するのは**散文だけ**です。`Prose.astro` が本文の位置に流し込みます。
  **原稿が何を書いても、ページの骨格は変わりません。**
- 「Company Analysis」「Design Brief」に相当する段階は**存在しません。**

### 生成プロンプトに何が入っているか

`projectContext()` は **project.json を丸ごと** Claude に渡しています（プロンプトキャッシュに載せて、
ページ間で課金されないようにしてある）。

> つまり **Claude は全項目を見ています。** 見ているのに、出力が散文だけなので、
> 「増やしたい仕事」も「利益率の高い仕事」も**文章の調子にしか影響できない。**

### 骨格はこの形に固定されています

```astro
<Base>
  <div class="page-head"><div class="inner"> h1 </div></div>
  <section class="section"><div class="inner">
    <Prose />          ← 生成された散文
    <Table /> or <Gallery /> or カード
  </div></section>
</Base>
```

**`.inner { max-width: 1040px }` が全ページ共通**で、
`.section + .section { border-top }` が唯一の区切りです。

> ご指摘の「全セクションを同じ幅」「同じ構造」「見出し→本文→カードの繰り返し」は、
> **この3行がそのまま原因**です。

### 会社情報が構造を変えている、現存する5箇所

意外に思われるかもしれませんが、**ゼロではありません。** ただし5つだけです。

| # | どこ | 何で変わるか |
|---|---|---|
| ① | `decidePages()` | `inquiry.goals`（集客／選別／採用／信用構築）で**生成するページが変わる** |
| ② | `site.ts` の `hasRecruit` / `hasMessage` | 同じく goals で**採用・代表挨拶ページの有無**が変わる |

**⑤が、いま最も筋が良い実装です。**「データが選択肢を左右する」という考え方が、
すでに一箇所だけ入っている。**これを全体の原理に引き上げるのが、今回の改修の本質**だと考えます。

## 4. 型・配色・書体・レイアウトの定義

すべて **`tool/lib/theme.ts`（338行）が単一の正**です。KOBOの画面もAstroの出力も、ここから作ります。

| 軸 | 数 | 何を持っているか |
|---|---|---|
| `palette` 配色 | 6 | 藍・鋼・深緑・臙脂・墨・琥珀。各9色（accent / ink / bg / line / **tableLine**） |
| `font` 書体 | 5 | ゴシック／明朝／見出しだけ明朝／丸ゴシック／Noto Sans JP |
| `mood` 雰囲気 | 3 | かたい／標準／やわらかい → radius・行間・字間・線の太さ・章の間隔 |
| `textSize` 文字サイズ | 3 | 17／18／20px。**1行の長さ(`--measure`)も連動** |
| `nav` メニュー | 2 | 上に横並び／左メニュー |
| `hero` 最初の画面 | 3 | 見出しを先に／写真を大きく（要・写真）／対応範囲を先に（要・対応範囲） |
| `sections` 章の区切り | 3 | 罫線／背景を交互に／余白だけ |
| `headings` 見出しの飾り | 4 | 飾らない／左に罫／下線／背景帯 |
| `tables` 表の罫線 | 3 | 全部に罫線／横罫だけ／行を縞に |

**型（PRESETS）は6つ**：標準／精密加工／老舗・職人／食品・環境／生活サービス／設計・技術。
**中身は上記9軸の値の組み合わせでしかありません。**

### 出力のされ方

- 色・書体・余白 → `themeVars()` が **CSS変数**を作り、`<html style="...">` に入る
- CSSで表せない差 → `<html data-nav data-hero data-sections data-headings data-tables>`

`site.css` の分岐は **36箇所**。内訳：

```
10  html[data-hero="photo"]      8  html[data-tables="stripe"]
 6  html[data-nav="sidebar"]     3  html[data-tables="horizontal"]
 2  html[data-sections="alternate"]  2  html[data-headings="rule"]
 2  html[data-headings="band"]   1  html[data-sections="space"]
 1  html[data-hero="spec"]       1  html[data-headings="underline"]
```

> **36箇所すべてが装飾です。** セクションの有無・順序・幅・強弱を変えるものは**1つもありません。**
> ご指摘の「会社固有の特徴が色変更だけで終わる」は、**文字どおりそうなっています。**

## 5. どこを変更すれば会社固有デザインになるか

### 5-1. 最大の発見：取材の★最重要ブロックが、サイトに届いていない

**サイトが一切参照していない27項目**のうち、ブロック2（引き合いの実態・20分・台本で★最重要）の項目：

```
inquiry.monthlyInquiries      月間の問い合わせ数
inquiry.channels              流入経路
inquiry.recentNewClientOrigin 直近の新規取引のきっかけ
inquiry.lostDealReasons       失注の理由
inquiry.mostProfitableWork    最も利益率の高い仕事
inquiry.wantMoreOf            もっと受けたい仕事
inquiry.wantLessOf            減らしたい問い合わせ
inquiry.outlookConcern        先行きの懸念
inquiry.targetKeywords        検索されたい言葉
```

**9項目のうち、サイトに届いているのは `inquiry.goals` ただ1つ**（ページの有無を決める）。

> **20分かけて聞いた、サイト全体の設計方針を決めるための情報が、
> 装飾にも構造にも一切使われていません。**
> ご指示の「原稿生成のためだけの情報と考えず、デザイン生成の素材として利用する」は、
> **まさにこの9項目のことです。**

（残りの18項目は `terms.*`・ドメイン・撮影日程など、**正しく社内向け**のものです。
`recruitment.retentionNotes` は今日 `internal: true` を付けました・D-170。）

### 5-2. 変更すべき箇所（影響の大きい順）

| 順 | 変えるもの | 今の状態 | どうするか |
|---|---|---|---|
| **1** | **ページ構造** | `.astro` にハードコード | **セクションの配列（データ）にする。** `decidePages()` と同じ層に `composeSections(project, brief)` を置く |
| **2** | **`.inner` の幅** | 全部 1040px | セクションごとに幅を持たせる（本文は狭く／表と写真は広く／数字は全幅） |
| 3 | **型の保存** | 保存していない（逆算） | 選んだ型のIDを `theme.direction` として保存する |
| 4 | **ブロック2の9項目** | サイトに届かない | Company Analysis の入力にする |
| 5 | **`theme` の意味** | 9軸の装飾 | 装飾は残し、**その上に「方向性」を足す**（置き換えない） |
| 6 | **`site.css`** | 344行・装飾のみ | セクション種別ごとの表現を足す |
| 7 | **生成の段数** | 1段（原稿のみ） | Analysis → Brief → Composition を足す |

### 5-3. 私の考える最小の構造変更

**テンプレートは1つのままでできます**（D-096を壊しません）。

```
project.json
   ↓
Company Analysis   ← 何で見せる会社か（数字／写真／技術／人／歴史）を判定
   ↓
Design Brief       ← 型（方向性）＋ 9軸の好み ＋ 分析結果 を統合
   ↓
composeSections()  ← ページごとに「セクションの配列」を返す
   ↓               　 { kind, 幅, 強さ, 参照するデータのパス }
Astro              ← 配列を描画するだけ。構造を持たない
```

**Astro側は「セクション種別ごとのコンポーネント」を持ち、どの順で何を出すかは持たない。**
これが「6種類のHTMLテンプレートを作らない」というご指示と両立する唯一の形だと考えます。

## 6. 設計上、必ず守らなければならない制約（改修で壊してはいけないもの）

ご指示にもありましたが、実装を読んだうえで**特に危ないもの**を挙げます。

| # | 制約 | なぜ危ないか |
|---|---|---|
| ① | **Analysis / Brief は、データの「値」を作ってはいけない** | 「精度を大きく見せる」は判断だが、「±5μm を大きく見せる」は**捏造**。段を増やすほど捏造の入口が増える。**Brief が出してよいのは「どのパスを、どう見せるか」だけ**にする |
| ② | `verifyDraft()` を通らない経路を増やさない | 表と一覧が Claude を通らないのは安全設計（D-095）。**セクション構成は Claude が決めてよいが、中身の値は必ず project.json から取る** |
| ③ | `{{要確認}}` と `unconfirmed` の流れ | 未確認の項目は**サイトに出さない**。セクションを増やすと「空のセクション」が出る危険がある。**データが無ければそのセクションを作らない**を原則にする |
| ④ | `internal: true` の欄 | 社内向けの欄が構図の素材として顔を出さないようにする（D-170） |
| ⑤ | **コントラスト検査** | `npm run test:contrast` は48件通っている。表現を増やすと**新しい配色の使い方が増える**ので、検査も広げる必要がある |
| ⑥ | 1行の長さ（`--measure`） | 幅を可変にすると**散文の1行が長くなる**。60代の読み手で最も効く要素（D-154）。セクションの幅を変えても、**散文だけは40em前後に保つ** |
| ⑦ | D-096「テンプレートは1つ」 | 保守工数がサイト数に比例した時点で、週15時間の運転は破綻する |
| ⑧ | 既存データの互換 | 取材済みの案件データは作り直せない。`migrateLayout()` と同じ配慮が要る |
| ⑨ | Cloudflare Pages の静的出力 | セクションを動的にしても、**出力は静的HTMLのまま**にする |

## 7. 費用について（判断材料）

現在は**1案件あたり Claude を通るのは原稿生成のみ**で、
`projectContext`（project.json 全体）をプロンプトキャッシュに載せています。

Analysis と Brief を足すと呼び出しが2回増えますが、
**同じキャッシュに乗るため、増えるのは主に出力分**です。原稿12ページ分に対して2回なので、
費用の増分は小さいと見込んでいます。ただし**実測していないので、断定はしません。**

# 段階1の結果（2026-09-13 実施）

**やったこと：トップページの骨格を、コードではなくデータで持つようにした**（D-180）。

```
project.json
   ↓
analyze()        lib/design/analysis.ts   何で見せる会社か（規則で判定・生成AIは使わない）
   ↓
composeTop()     lib/design/sections.ts   セクションの配列（種類・幅・強さ）
   ↓
index.astro                               配列を描くだけ。骨格を持たない
```

## 松原精機で、何が変わったか

| | 前 | 後 |
|---|---|---|
| セクション数 | 2 | **6** |
| 幅の種類 | **1**（1040pxのみ） | **3**（1040／760／1230） |
| 構成の決まり方 | `.astro` に固定 | **案件データから** |

**見立て（実データ）：**

```
  7  declined   他社様で断られた案件を受けた記録がある
                ／価格で比べられる引き合いを減らしたいとのことなので前に出す
  6  technique  工程の工夫が、取材の追い質問で言葉になっている
  4  numbers    ロット・納期・精度が数字で聞き取れている
  4  materials  対応材質に幅がある／増やしたい仕事があるので、対応できる範囲を前に出す
  2  equipment  メーカー・型番まで分かっている設備がある
  1  people     人を出せる材料がある
  1  history    沿革と代替わりが聞き取れている
```

**「価格で比べられる引き合いを減らしたい」「増やしたい仕事がある」は、
これまでサイトに一切届いていなかった項目です**（ブロック2）。いま順番を動かしています。

## 会社が違えば構成が違うこと（`npm run test:design`・15件）

```
①断りを受ける会社: hero → declined → technique
②設備の会社      : hero → figures → equipment → materials
③老舗の会社      : hero → people → timeline → gallery
```

**材料が無ければ、そのセクションを作りません。**
材料が何も無い会社では、最初の画面だけになります。仮の画像は写真として数えません。
沿革が2件では年表を作りません（**薄い年表は、無いより悪い**）。

## 正直に言うこと：型を変えても、まだ構成はあまり変わりません

同じ会社で6つの型を試すと、変わるのは「最初の画面」に連動する部分だけです。

```
型「標準」      hero → declined → cases → technique → figures → materials
型「精密加工」   hero → declined → cases → technique → materials → equipment
型「老舗・職人」  hero → declined → cases → technique → figures → materials
```

**これは段階1の範囲どおりです。** 型を「デザインディレクション」にするには、
**選んだ型のIDを保存する必要があり**（今は9軸の値だけを保存し、型は逆算している・第3章）、
それは段階2で行います。

段階1で実装したのは「**会社が変われば構成が変わる**」ほうです。

## 段階2以降に残っていること

1. **型の保存とディレクション化** — `theme.direction` を足し、型ごとに見せ方の優先順位を変える
2. **トップ以外のページ** — 強み・技術／対応可能範囲／設備一覧／事例。いまも `.astro` 固定
3. **Design Brief の段** — 型 ＋ 見立て ＋ 9軸を統合する層
4. **生成原稿との連携** — 構成が決まってから原稿を書けば、セクションに合った文章になる
5. **コントラスト検査の拡張** — 新しいセクションの色の使い方は、まだ検査に入っていない

# 段階3-1：コントラスト検査の拡張（2026-09-13 実施）

アドバイザーの判断で、段階3は**検査の拡張から**始めた。
表現を足した分だけ、読めない配色が混ざる余地が増えていたため（D-191）。

## 足した組み合わせ（48件 → 84件）

| 追加した検査 | どこの話か | 下限 |
|---|---|---|
| 本文（薄い背景の上） | 強みの札・表の見出し・脚 | 4.5:1 |
| 補助文（薄い背景の上） | 同上 | 4.5:1 |
| 小見出し（札の中） | `.point-sub`（取材メモの【】見出し） | 4.5:1 |
| 表の見出し（縞のとき） | 行を縞にした表の行見出し | 4.5:1 |
| 表の罫線（薄い背景の上） | 行見出しの列・スマホの縦積み | 3:1 |
| 章の目印（帯・線・点） | 引用の縦線・札の縦線・設備カードの上辺・年表の点 | 3:1 |

## 実在の欠陥が1件見つかった

**表の罫線を、白地でしか測っていなかった。**
既定の表では**行見出しの列が薄い背景**になっており、そこでは全6配色が下限を割っていた。

```
藍 2.78 ／ 鋼 2.87 ／ 深緑 2.93 ／ 臙脂 2.80 ／ 墨 2.76 ／ 琥珀 2.89　（3:1 必要）
```

6配色とも罫線を濃くして解消した（例：藍 `#929599` → `#898c90`）。

## 検査が知らない色を、静かに増やさないようにした

段階1・2で**`--accent-dark` を薄い背景の上に置く**という新しい組み合わせが生まれていた。
**気づいたのは偶然だった。**

スタイルシートを読んで、検査が知らない色が `color:` や `background:` に使われていたら止める。

```
✗ 検査が知らない色の使い方があります
      文字色 --accent-soft
  **site.css に色を足したら、この検査にも組み合わせを足してください。**
```

## 検査を通したあとに、画面を見て見つけた欠陥（D-192）

**「行を縞に」は、PC表示で罫線が1本も無かった。** 区切りは背景色の差だけ。

ところが白地と薄地の差は、**全6配色で 1.08〜1.10:1** しかない。
**実測すると、ほぼ見分けがつかない。**
「行数が多い表で目が迷わない」ために選ぶ型なのに、区切りが見えないのでは意味がない。

これは**コントラスト比の検査では捉えられない種類の欠陥**だった。
下限の数字は置かず（根拠がないので・D-162）、縞を補助にして罫線を主にする形に変えた。

> **数字の検査は必要だが、十分ではない。** 通ったあとに、必ず画面を見る。

# 段階3-2：構成が決まってから原稿を書く（2026-09-13 実施）

## 何が問題だったか

**構成と原稿が、別々に決まっていました。**

原稿を書く側は、どのセクションがどの順で出るかを知りません。
そのため、**すぐ下に材質の札が出ているのに、原稿でも材質を並べる**ことが起きます。

## 直したこと（D-193）

生成の段で、書き出しと**まったく同じ関数**（`analyze()` → `composeTop()`）を先に呼び、
その結果を指示に含めるようにしました。

```
## この会社の見立て（聞き取りから機械的に判定したもの）

2位 工程の工夫が、取材の追い質問で言葉になっている
3位 ロット・納期・精度が数字で聞き取れている

**型「精密加工」**（条件と設備で判断してもらう）で組み立てます。

1. hero　… 会社名・事業の概要・対応材質や納期の一覧・外観写真

**すでに出ているものを、文章で繰り返さないでください。**
あなたが書くのは、**その前後をつなぐ文脈**と、**データだけでは伝わらない理由**です。
```

## 作業中に見つかった食い違い（D-194）

## 社内の判断材料を書かせない（D-195）

D-182で「引き合いの実態は順番を動かすためにだけ使う」と決めましたが、
**その規則は構成の側にしか無く、原稿を書く側には伝えていませんでした。**

案件データは丸ごと渡しているので、
「最も利益率の高い仕事は試作と小ロット」と書かれてしまう余地がありました。
**利益率を公開する会社はありません。**

共通ルールに、該当項目を名指しして書かないことと、
その代わりに何をすべきか（**安さではなく難しさで選ばれる書き方にする**）を入れました。
