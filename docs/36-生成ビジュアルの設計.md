# 第9段階 設計案 — AI生成ビジュアルによる、その会社の視覚世界

**これは設計案である。コードはまだ1行も変えていない。**
アドバイザーのレビューを受けてから実装に入る（第6・第7段階と同じ手順）。

---

## 0. 結論から

**画像生成APIは、いまこの環境では使えない。** 理由は2つあり、どちらも回避しない。

1. **Anthropic API は画像を生成しない。** SDKの資源は `messages` / `beta` / `skills` の3つだけで、
   画像は**入力として読める**が、出力として作れない（実測：`node_modules/@anthropic-ai/sdk/resources/`）。
2. **鍵が無い。** `ANTHROPIC_API_KEY` も `ANTHROPIC_AUTH_TOKEN` も未設定。
   他社の画像生成SDKも鍵も入っていない。

→ ご指示のとおり **Phase F（生成API接続）は実装しない。**
**Generated Visual Brief を作って保存するところまで**を今回の範囲とする。

**それでも今回の価値は小さくない。** 出来上がるのは次の3つである。

| | |
|---|---|
| ① **Visual Language** | その会社を「どういう視覚世界として表現するか」を、会社データから決めて保存する |
| ② **Generated Visual Brief** | 2〜4枚ぶんの、**会社ごとに違うプロンプト一式**（余白・焦点・モバイルの切り取りまで指定） |
| ③ **受け皿** | 画像が届いた瞬間に、正しい帯へ・正しい役割で・崩れずに入る配線と検査 |

③があるので、**画像は外で作って持ち込める。** 生成の手段が変わっても設計は変わらない。

## 1. 既存Asset Systemで再利用できる部分（＝新しい概念を作らなくてよい部分）

**結論：`generated` は、すでに語彙として正式に存在し、型の上で `atmosphere` 専用になっている。**

```ts
// lib/design/system/asset.ts（現行・無変更）
ALLOWED = {
  evidence:   ["customer", "none"],                          // ← generated は入れない
  atmosphere: ["graphic", "library", "generated", "none"],   // ← すでに許可されている
}
```

| ご指示の要件 | 既存で足りるか |
|---|---|
| generated は atmosphere のみ | **足りる。** `ALLOWED` が構造で禁じている（注意書きではない） |
| evidence に generated を使わせない | **足りる。** `intentOf(content)` が内容から機械的に決める。`cases/equipment/photos/profile/executive/recruit` は evidence 固定 |
| customer photo と役割を混ぜない | **足りる。** 実写は `wanted`（依頼）と `customer` 経路、生成は別経路 |
| role（lead / support / background / decoration） | **足りる。** 4つで表せる |
| subject | **足りる。** AI画像は抽象・コンセプチュアルに限るので、使うのは `geometry` `light` `texture` `grid` `dimension` の**描ける5つだけ**。`workpiece` `facility` `person` などの**実写主題は生成に使わせない**（＝「工場写真の代用品」を型で禁じる） |
| 1ページ1枚まで・地の素材を隣り合わせにしない | **足りる。** `library` に課した規則（D-324）をそのまま使う |

**新しい `AssetSource` も `AssetSubject` も `surface` も `motif` も `presentation` も増やさない。**

---

## 2. 新規に必要な部分

足りないのは**「何のために生成するのか」を持つ層**だけである。2つ作る。

### ① Visual Language（`lib/design/system/visual-language.ts`）

**「何を描くか」ではなく「この会社をどういう視覚世界として表現するか」。**
`surface` / `motif` / `graphic` / `library` とは重ならない——あれらは**描き方**、こちらは**方針**である。

```
勝ち筋（primaryStrength）→ 視覚世界の軸
  precision   measurement / controlled geometry      計測・座標・公差
  difficulty  transformation / process / complexity  変形・工程・複雑さ
  craft       material / texture / accumulated time   素材・手・時間
  engineering structure / system / technical geometry 構造・系・製図的幾何
  industrial  scale / repetition / production         規模・反復・流れ
  product     object / material / engineered form     物・素材・設計された形
  （汎用 record / reason / person も同じ形で持つ）
```

**これだけでは会社の差が出ない**（同じ勝ち筋の会社が全部同じ画像になる）ので、
会社データから**4つの修飾**を足す。ここが「会社ごとの差」の実体である。

| 修飾 | どこから決まるか | 例（同じ precision でも） |
|---|---|---|
| `material` | `capability.materials` | アルミ主体→白い金属／鋳鉄・鋼→暗い金属／樹脂→半透明 |
| `mood` | `direction.tone` ＋ `mood`（かたい/標準/やわらかい） | katai→硬質・高コントラスト／yawaraka→静か・低コントラスト |
| `density` | `mood.typeScale` と帯の余白（第7段階⑥） | 詰める型→密／ゆるい型→疎 |
| `light` | `palette` の明暗と `surface` の既定 | dark面を持つ型→ドラマチック／plain主体→均質光 |

> **会社A（アルミ・標準・明るい面）** … white metal / measurement / controlled light / minimal
> **会社B（鋳鉄・かたい・暗い面）** … dark metal / cutting / technical / dramatic
> **会社C（ステンレス・やわらかい）** … brushed metal / geometry / soft light / calm
>
> **同じ `precision` でも、材質・型・面から別の絵になる。** 乱数は使わない。

### ② Generated Visual Brief（`lib/design/system/generated.ts`）

ご指示の項目をすべて持つ。**モバイルと権利も最初から持たせる。**

```ts
interface GeneratedVisual {
  visualId: string;          // 会社ハッシュ＋用途で決まる（同じ入力なら同じID＝再生成しない鍵）
  purpose: "firstView" | "strength" | "company" | "peak";
  subject: "geometry" | "light" | "texture" | "grid" | "dimension";
  direction: string;         // 型のID
  language: VisualLanguageId;
  mood: string; composition: string; material: string; lighting: string;
  aspectRatio: string;       // "16:9" | "4:3" | "1:1"
  placement: { page: string; content: ContentId; role: AssetRole };
  // ── モバイル（ご指示） ──
  focalPoint: { x: number; y: number };   // 0〜1。切り取りの中心
  cropSafe: { mobile: string };           // "1:1" など、縦でも意味が消えない比
  textSafeArea: "left" | "right" | "top" | "bottom" | "none";
  prompt: string; negativePrompt: string;
  // ── 権利と来歴（ご指示） ──
  provider: string;          // 生成に使ったサービス。**人が入れる。こちらが騙らない**
  generatedAt?: string; commercialUse?: string; file?: string;
  status: "brief" | "ready" | "failed" | "skipped";
  source: "generated";       // リテラル固定
}
```

**`negativePrompt` は飾りではない。** ご指示の禁止リスト（stock photo風・generic factory・
random worker・fake equipment・他社ロゴ…）を**毎回そのまま入れる**ための欄である。

## 3. 流れ（既存の Design Brief と同じ形にする）

```
project.json → analyze() → designBrief → **visualLanguage** → **generatedVisuals[]**
                                              ↑ 規則版が既定。AIは提案（第5段階と同じ）
build-site は保存されたものを読むだけ（AIも生成も呼ばない）
```

**AIに決めさせるもの**：visual language / purpose / subject / mood / composition / lighting /
placement / visual intensity（＝ご指示どおり）。
**AIに決めさせないもの**：ページの存在・URL・navigation・事実・数値・認証・設備・顧客の証拠・SEO構成。
**既存の `brief-ai.ts` の枠組み（語彙IDだけ返させる・5段検査・落ちたら規則版）をそのまま使う。**

## 4. 保存場所

| もの | 置き場所 | 理由 |
|---|---|---|
| Visual Language・Brief | `project.json` の `visualLanguage` / `generatedVisuals[]` | `designBrief` と同じ。**再現性の鍵（`sourceProjectHash`）も同じ仕組み** |
| 画像そのもの | `projects/<ID>/generated/` | **`photos/` と分ける。** 混ぜると「実写か生成か」が一覧で分からなくなる |
| 書き出し先 | `site-template/public/generated/` | `public/photos/` と同じ扱い（Git管理外） |

---

## 5. 配置（Wikipedia的構成にしない）

**画像カードを足さない。** 既存の presentation / layout と組み合わせる。

| 場所 | 組み方（すべて既存語彙） |
|---|---|
| ファーストビュー | **hero の地**に敷く（`--asset-image`。`library` と同じ仕組み）。**hero語彙は増やさない。** 見出し・対応範囲の札・値はそのまま上に乗る＝「AI画像＋普通の見出し」にならない |
| 強み・技術 | `layout="split"` の**片側**。左＝生成ビジュアル／右＝一言。実写があるなら**左＝生成・右＝実写**（世界観と実物を同時に見せる・ご指示） |
| 会社・代表 | `role="background"` で地に沈める。文字が主役のまま |
| 中盤の山 | `width="full"` ＋ `peak="image"`（既存）。ただし**実写があるときは実写を優先**する |

**上限2〜4枚。**「画像が無いほうが美しい場合は作らない」を、
**`none` は失敗ではない**（既存の原則①）としてそのまま適用する。

---

## 6. fallback

既存の順序（`graphic` → `library` → `none`）の**手前に何も足さない。**
生成は**最後の選択肢**で、`status !== "ready"` または画像が実在しなければ、
その帯は**いままでと1ピクセルも変わらない**。

鍵なし／API不可／timeout／rate limit／壊れた応答／生成失敗——**すべて `brief` のまま据え置き、
サイトは最後まで書き出す**（`decideBrief` と同じ約束）。

---

## 7. 再生成しない（determinism）

`visualId` は**会社データのハッシュ＋用途**から決まる。
`status: "ready"` かつファイルが実在するなら、**通常のビルドでは作り直さない。**
明示的に `npm run visual -- <ID> --regenerate` と言われたときだけ作り直す。
**2回ビルドしてHTMLが1バイトも変わらないことを検査で見る**（第8段階⑥で使った方法）。

---

## 8. 検査（ご指示の項目をそのまま）

generated は atmosphere のみ／evidence になれない／実写と役割が混ざらない／
生成が無くてもビルドできる／404が無い／placeholder にならない（`internal-language` の
「仮の画像」検出を**生成画像にも当てる**）／モバイルで横スクロールが出ない／空帯が無い／
内容が減らない／ページ構成・URL・sitemap が変わらない／2回ビルドが一致／
既存の asset 試験と contrast 試験が緑のまま。

**加えて1つ足す**：**生成画像が実写主題（workpiece / facility / person …）を取れないこと。**
これが「工場写真の代用品にしない」の実体である。
