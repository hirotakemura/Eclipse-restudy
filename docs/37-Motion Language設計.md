# 第9段階 設計案 — Motion Language（サイト全体の情報体験を設計する）

**コードは1行も書いていない。** 現在の実装を実際に動かして測り、設計だけを置く。

**この改訂で目的を変えた。** 旧版は「生成ビジュアルが動いていない」を課題にしていた。
それは症状であって病気ではない。**本当の課題は、サイト全体を通したときに
動き・展開・間が不足していて、静的な情報サイトに見えることである。**

---

## 0. 結論から

### 0-1. 足りないのは「動きの種類」ではない。**「当たる対象」と「対比」である**

| 問い | 答え |
| --- | --- |
| `@keyframes` を増やす必要があるか | **無い。** 3つで足りる |
| いま3つとも動いているか | **動いていない。** 松原精機の全13ページで、実際に走っているのは `kobo-rise` だけ |
| なぜ静的に見えるか | **全部の節が、同じ動きを、同じ範囲で、同じだけやっているから。** 5回同じことが起きるのはリズムではない |
| どうすれば体験になるか | **動かす節を増やすのではなく、動かさない節を作る。** リズムは対比でしか生まれない |

### 0-2. 測った事実（すべて実際にブラウザで動かして確認した）

**① 実案件は `subtle` で出荷されている**

`projects/matsubara-seiki/project.json` には `direction` が**書かれていない**。
`getDirection(undefined)` は既定の `standard`（標準）を返し、その `motion` は `subtle`。
書き出された HTML も `data-motion="subtle"`。

**② `subtle` で実際に動いている要素は、トップページで5個。全部同じもの**

```
── data-motion="subtle" ──   動いている要素 5個
      5  kobo-rise @ section        ← 帯が5つ。それだけ

── data-motion="standard" ── 動いている要素 14個
      5  kobo-rise @ section
      5  kobo-rise @ LI             ← 並びの遅れ
      4  kobo-rise @ SPAN
```

**`standard` にしても、走るのは `kobo-rise` だけである。**

**③ `kobo-grow` と `kobo-reveal` は、全13ページで一度も走らない**

| 動き | 当たる対象 | 松原精機のサイトでの実数 |
| --- | --- | --- |
| `kobo-grow`（線が伸びる） | `.band[data-motif="process"]` | **0** |
| `kobo-reveal`（覆いが外れる） | `.gallery / .hero-photo / .photo` の `img` | **0** |

**サイト全体の `<img>` タグは 0 個である。** 実写が1枚も無い。
つまり**3つある動きのうち、実際に使われているのは1つだけ**で、残り2つは対象が存在しない。

**④ 最初の画面（hero）は、どの型でも一度も動かない**

hero は `<section class="hero">` であって `.band` ではない。
動きの規則はすべて `.band` に当たっているので、**hero には最初から1つも当たっていない。**
（前回検証した `kobo-reveal` を生成ビジュアルに当てても、hero はページ先頭なので `entry` が起きず動かない。）

**⑤ 15型のうち10型は、この「帯が現れるだけ」しか持っていない**

`subtle` 9型（standard / craft / industrial / seikatsu / shop / gstandard / editorial / luxury / human）
＋ `none` 1型（classic）＝ **10型**。`standard` は5型（technical / engineering / product / modern / dynamic）。

**⑥ 山は、13ページ中11ページで「最初の帯」にある**

```
index        hero → vast*statement → normal → normal → loose → loose*spec → cta
strengths    vast*statement → normal → normal → tight → cta
capability   normal → normal → loose*spec → normal → cta      ← 山が3番目。例外
company      vast*spec → normal → cta
equipment    loose*spec → cta
cases/1      normal → vast*process → cta                      ← 山が2番目。例外
recruit      loose*statement → cta
```

**ページは山から始まって、あとは下っていく。** 「静 → 動 → 静 → ピーク → 静」という
上り坂は、**いまのページ構成からは作れない。**（これは Motion の問題ではない。→ 最終節）

**⑦ ページによっては、時間の軸そのものが無い**

| ページ | PC | SP |
| --- | --- | --- |
| index | 5.0 画面分 | 6.7 画面分 |
| strengths | 3.9 | 5.6 |
| company | 2.4 | 3.4 |
| **equipment** | **1.7** | 2.6 |
| **recruit** | **1.5** | 1.8 |

**1.5画面のページに時間の構成は作れない。**

### 0-3. したがって、Motion Language の仕事はこうなる

```
×  新しい動きを足す
×  各要素にアニメーションを割り当てる
○  どの節を動かし、どの節を止めるかを、ページ単位で決める
○  いまある3つの動きに、当たる対象があるかを確かめる
```

## A. Motionの目的

**Motion は装飾ではない。情報の「順序・関係・重要度」を、時間で伝えるものである。**

| Motion が担うこと | Motion が担わないこと |
| --- | --- |
| どれを先に読むか（**順序**） | 何を書くか |
| どれとどれが同じ仲間か（**関係**） | どこに置くか |
| どれがこのページの主役か（**重要度**） | 読みやすさ（余白・文字組の仕事） |
| どこで一息つくか（**間**） | 情報量の不足を埋めること |

### 4つの原則（例外なし）

1. **動きそのものを見せない。** 読み手は調達担当者と設計者で、演出を評価しに来ていない
2. **動きが無くても情報構造が成立する。** 素の HTML は最初から全部見えている
3. **「動かさない」が既定である。** 動かすには理由が要る
4. **動かす理由は、会社データに根拠がなければならない**（D-205 と同じ。推測で動かさない）

### この設計が目指す状態

> スクロールしていくと、**どこが本題で、どこが補足で、どこで終わりか**が、
> 読む前に分かる。動いていることには気づかない。

## B. Motion Vocabulary

### B-1. 語彙は3つ。**増やさない**

| 語彙 | 実装 | 何が起きるか | 意味 |
| --- | --- | --- | --- |
| `rise` | **既存** `kobo-rise` | 透明度 .35 → 1／10px 下から上へ | **そこに情報がある**と知らせる |
| `draw` | **既存** `kobo-grow` | 縦に `scaleY(0) → 1` | **順序・工程・つながり** |
| `reveal` | **既存** `kobo-reveal` | `clip-path` の覆いが外れる＋`scale(1.02) → 1` | **物が現れる**（面・写真） |
| `none` | — | 動かない | **既定** |

### B-2. 「既存3種だけでサイト全体の体験を作れるか」への回答

**語彙としては足りている。ただし、いまは実質1種類しか動いていない。**

| | 語彙はあるか | 当たる対象はあるか | いま動くか |
| --- | --- | --- | --- |
| `rise` | ○ | ○（帯・並び） | **○** |
| `draw` | ○ | **×**（`data-motif="process"` が 0） | × |
| `reveal` | ○ | **×**（`<img>` が 0。背景には当てられない※） | × |

※ 前回の検証（実測）で、`reveal` を生成ビジュアル（帯全面の `::before`）に当てても
**切り取りが見える位置が1つも無い**ことを確認した。`animation-range: entry 0% entry 45%` は
「帯の上から45%が入った時点で終わり」だが、`kobo-reveal` が切るのは**帯の下端12%**で、
そこが画面に入るのは entry 88% 以降である。**終わったあとにしか見えない場所を切っている。**
加えて `scale(1.02)` が横に 11px（PC）／4px（SP）はみ出す。**不採用と判断済み。**

**つまり足すべきは `@keyframes` ではなく、`draw` と `reveal` が当たる対象である。**
対象とは、工程モチーフの帯と、実写の写真。**どちらもコンテンツ側の話**である（→ 最終節）。

### B-3. 見送る語彙

| 候補 | 判断 | 理由 |
| --- | --- | --- |
| `trace`（なぞる） | 見送り | `draw` と実質同じ。SVG 線画を持っていない |
| `assemble`（組み上がる） | 見送り | **既存の stagger がこれである。** 名前を足すと二重管理 |
| `flow`（流れる） | 見送り | 常時ループは禁止。一方向にすると `rise` と区別がつかない |
| `shift`（ずれる） | 見送り | layout shift の禁止と衝突する |
| `blur`（ぼけが晴れる） | 見送り | `filter` は描画負荷が高く、文字に掛かると可読性を壊す |

## C. Motion Axis（動きの軸）

**軸は「どの語彙を使うか」ではなく、「何を動かし、どの程度にするか」を決める材料である。**
軸 → 語彙の1対1の対応表は作らない。

| 軸 | 時間の性質 | 画面で何が変わるか |
| --- | --- | --- |
| `settle`（静まる） | 一度だけ、静かに定位置に収まる | 移動量は最小。stagger を使わない。範囲は長め＝ゆっくり |
| `sequence`（順に） | 段階的に。一度に完成しない | stagger と `draw` が主役。並びの意味が読める |
| `arrive`（届く） | 短く、続けて、間を置かない | 範囲は短め＝きびきび。stagger の間隔を詰める |
| `emerge`（現れる） | 覆いの下から物が出る | `reveal`。**当たる対象（写真）があるときだけ** |
| `none` | 動かさない | 何も起きない |

## D. Trigger（引き金）

**JavaScript は使わない。現在サイトにアニメーション用の JS は1行も無い。**

| 引き金 | 実装 | 使う場面 | 判断 |
| --- | --- | --- | --- |
| スクロールで入ってきたとき | **既存** `animation-timeline: view()` ＋ `animation-range: entry 0% entry N%` | すべての「現れる」動き | **これだけを使う** |
| 操作したとき | **既存** `transition`（`--m-fast: .18s`） | focus / リンクの下線・色 | 既存のまま |
| 読み込み直後 | — | — | **禁止**（N 参照） |
| 時間経過 | — | — | **禁止**（常時ループ） |
| IntersectionObserver | 無し | `animation-timeline` 非対応環境 | **入れない。** 非対応では**何も起きない**のが正しい（D-240） |

**「間」を作る唯一の道具は `animation-range` である。**
範囲を長くすれば同じ動きがゆっくりになり、短くすればきびきびする。
既存の値：帯 40% ／ stagger 35→46→57→68% ／ 工程 50% ／ 写真 45% ／ 山 55%。
**この道具はいま stagger にしか使われていない。** ここが最も伸びしろがある。

**`animation` の一括指定は使わない**（D-295）。圧縮が `animation-timeline` を畳み、
ブラウザが declaration ごと捨てる。**謳っている動きが1つも動いていなかった**実例がある。

## F. Intensity（強さ）

**既存の3段階（`none` / `subtle` / `standard`）をそのまま使う。新しい語彙は作らない。**
ただし**中身を作り直す。** いまの `subtle` は「帯が現れるだけ」の1規則しか無く、
**既定でありながら、体験としての設計が入っていない。**

| | 使う拍（G 参照） | 動く対象 | 誰に当たるか |
| --- | --- | --- | --- |
| `none` | `still` のみ | 何も動かない | `classic`／動きを嫌うお客様／根拠が `unknown` |
| `subtle` | `still` ＋ `settle` ＋ **`peak`** | 帯／**山だけ長め** | **既定。15型中9型。`direction` 未設定の案件もここ** |
| `standard` | 4拍すべて | ＋並びの遅れ／工程の線／写真 | 5型 |

**`subtle` に「山」を入れるのが、この設計で最も効く1点である。**
`.band[data-peak]` の「長い範囲でゆっくり現れる」は**新しい動きではなく、既存 `kobo-rise` の範囲違い**にすぎない。
いまこれは `standard` 限定なので、**10型のサイトには山が無い。**
→ 実装可否は **P-2**（社長の承認が要る）。

**時間の値（`--m-fast .18s` / `--m-rise .5s` / `--m-peak .7s`）は増やさない。3つで足りている。**

## G. Page-level rhythm ★

### G-1. いま何が起きているか

トップページの5つの帯は、**全部が同じ `kobo-rise` を、同じ `entry 0% → 40%` で行う。**

```
hero      ［動かない］
帯1 山    ▁▂▃▄▅ rise 40%
帯2       ▁▂▃▄▅ rise 40%
帯3       ▁▂▃▄▅ rise 40%
帯4       ▁▂▃▄▅ rise 40%
帯5 準山  ▁▂▃▄▅ rise 40%
CTA       ［動かない］
```

**同じ出来事が5回起きている。** これはリズムではなく、繰り返しである。
山（帯1）も準山（帯5）も、ほかと**まったく同じ**に見える。

### G-2. 設計：**拍（beat）**

ページを、節ごとの**4つの拍**の並びとして設計する。**拍は既存データだけから決まる。**

| 拍 | 何が起きるか | どの節に付くか |
| --- | --- | --- |
| `still`（静） | **何も動かない。帯も動かない** | hero ／ CTA ／ **山の直前の節** |
| `settle`（寄る） | 帯だけが静かに現れる（いまの `subtle` と同じ） | 通常の節 |
| `open`（開く） | 帯＋**本体の並びが順に**（stagger）。工程なら線（`draw`） | 並びを持ち、`density` が `loose` / `vast` の節 |
| `peak`（山） | 帯が**長い範囲**で現れる。主役が写真なら `reveal` | `data-peak` のある節。1ページ最大2つ |

**決める材料は、すでに全部ある。**

| 材料 | 出どころ | いまの状態 |
| --- | --- | --- |
| `data-density`（tight/normal/loose/vast） | `visual.ts` が算出。**同じ濃さが3連続しない規則もある**（`visual.ts:228`） | 出ているが**動きには使われていない** |
| `data-peak` | `visual.ts`。山と準山 | 出ている。`standard` のときだけ長さに使う |
| 節の位置（先頭／末尾） | DOM 順 | 使われていない |
| 並びを持つか | `.cards` `.chips` `.process` 等の有無 | stagger の当たり先として使われている |

### G-3. 拍を並べる規則（これが設計の本体）

1. **`still` を必ず1つ以上置く。**「間」は、動かさない節でしか作れない
2. **山の直前を `still` にする。** 山が山に見えるのは、直前が静かなときだけ
3. **`open` を2節続けない。** 連続すると動きが常態になり、山との差が消える（既存の density 連続禁止と同じ思想）
4. **CTA は常に `still`。** 押す場所は動かさない
5. **hero は常に `still`。** 開いた瞬間に動かさない
6. **動く節は、全節の半分以下。** 節が3つ以下のページは**動く節を1つだけ**にする
7. **1ページの `peak` は最大2つ**（山と準山）。3つ目は山ではない

### G-4. いまのページ構成で作れる形

山は先頭にあるので、**上り坂（静→動→静→ピーク→静）は作れない。**
作れるのは**「山から始まり、間を置いて、もう一度だけ立ち上がって、静かに終わる」**形である。

```
＜トップページ・提案＞
hero       still    ［動かない］              ← 静
帯1 山     peak     ▁▂▃▄▅▆▇ 長い範囲          ← 動（ここが本題だと分かる）
帯2        still    ［動かない］              ← 静（間）
帯3        settle   ▁▂▃▄▅                    ← 弱い動
帯4        still    ［動かない］              ← 静（間）
帯5 準山   peak     ▁▂▃▄▅▆▇ 長い範囲          ← 動（もう一度だけ）
CTA        still    ［動かない］              ← 静
```

**動く節は 5 → 3 に減る。** それでも「静 → 動 → 静 → 弱動 → 静 → 動 → 静」になる。

> **リズムは、動かす量を増やして作るのではない。動かさない節を作って作る。**

### G-5. 短いページ

| ページ | 節 | 提案 |
| --- | --- | --- |
| `equipment`（2節・1.7画面） | 山 → CTA | `peak` → `still`。**それ以上は入れない** |
| `recruit`（2節・1.5画面） | 山 → CTA | 同上 |
| `company`（3節） | 山 → 通常 → CTA | `peak` → `still` → `still` |
| `cases/N`（3節） | 通常 → 山(工程) → CTA | `still` → `peak`（`draw` が効く）→ `still` |

**1.5画面のページで拍を刻もうとしない。** 出来事は1つで足りる。

### G-6. サイト全体のリズム

ページ間でも同じ考え方を使う。**全ページが同じ強さで動くと、サイト全体が平坦になる。**

| ページ群 | 拍の濃さ | 理由 |
| --- | --- | --- |
| トップ | 最も濃い（`peak` 2つ） | 最初に見る。ここでサイトの性格が決まる |
| 強み・対応範囲・事例 | 中（`peak` 1つ＋`open` 1つ） | 読ませるページ |
| 会社概要・設備・採用・問い合わせ | 最も薄い（`peak` 1つのみ、あとは `still`） | 調べに来るページ。**探している人を動きで邪魔しない** |

## H. Section-level rhythm

**1つの節の中で起きてよい出来事は、最大2つ。**

```
節の出現（帯の rise）           ← 出来事①
   ↓
本体の並びが順に（stagger）     ← 出来事②（並びがあるときだけ）
```

| 規則 | 理由 |
| --- | --- |
| **見出しを単独で動かさない** | 見出しと帯は1つの出来事。分けると同じ話が2回始まる |
| **リード文を動かさない** | 読み始めが遅れる |
| **出来事を3つ以上にしない** | 節の中で視線が3回止まると、読む前に疲れる |
| **stagger は最大4段** | 既存の `nth-child(n+4)` でまとめてある。5個目以降が待たされ続けない |
| **表・比較は行単位で動かさない** | 一度に読むものだから |
| **本文・引用は動かさない** | 読むものは動かさない |

**節の中の順序は、必ず読む順序と同じにする。** 下から先に現れる、右から先に現れる、は禁止。

## K. Reduced Motion

**既存の作りを変えない。すべての新規規則も同じ枠の中に書く。**

1. 動きは `@media (prefers-reduced-motion: no-preference)` の**中だけ**
2. **初期状態を `opacity: 0` にしない。** 素の HTML は最初から見えている
3. **動きによって初めて情報が出る設計は禁止**
4. `@supports (animation-timeline: view())` で囲う。**非対応環境では何も起きない**
5. `@media print` で動きを止め、本文を残す
6. `focus-visible` は動きの設定と無関係に常に出す（`prefers-reduced-motion` の**外**にある）

**実測（前回の検証）**：`prefers-reduced-motion: reduce` では
`animation-name: none` ／ `clip-path: none` ／ `transform: none` ／ 透明度は指定どおり。
**横のはみ出しも 0px。** この枠は正しく効いている。

**検査**：`design.test.mjs` が `prefers-reduced-motion` ブロックを全部走査して
`opacity: 0` の焼き込みを見ている。**新しい規則も同じ検査に通す。**

## N. 禁止事項

**ご指示の禁止候補を、1つずつ判定した。**

| 候補 | 判定 | 理由 | 現状 |
| --- | --- | --- | --- |
| **page load fade** | **禁止** | 開いた瞬間に動かすと、読み手が最初にするのが「待つこと」になる。`@supports` を外した場合に起きる事故そのもの | 無し（正しい） |
| **page transition** | **禁止** | 静的サイトで遷移演出を入れると、体感が**遅くなる**。調達担当者は速さを評価する | 無し |
| **parallax** | **禁止** | 意味が無く、前庭障害の主因。生成ビジュアルは `::before` の背景なので特に誘惑があるが**入れない** | 無し |
| **infinite loop** | **禁止** | 常時動くものは「読む」を妨げ続ける。`industrial` の「繰り返し」もループでは表さない | 無し |
| **count-up** | **禁止** | 我々が出す値は「±0.005mm」「標準7日。急ぎの場合は最短3日」という**文字列**で、数として数え上げられない。数えられる形に言い直すのは**こちらが値を作ること**（D-181・D-240） | 無し（取り下げ済み） |
| **hover zoom** | **禁止** | 指とカーソルの下で対象が変わる。写真の拡大は `reveal` と意味が衝突する | 無し |
| **hover shadow** | **禁止** | 影の変化は面の高さの変化に見え、**平らな紙という設計**と衝突する | 無し |
| **moving text** | **禁止** | **読むものは動かさない。** 例外なし | 無し |
| **layout shift** | **禁止** | 位置が動いて他がずれるものはすべて。`transform` は許すが `margin` / `height` / `top` は動かさない | 無し |
| **大きな移動量** | **禁止** | 上限は**既存の 10px**。これを超える値を新設しない | ○ 10px |
| **過剰な stagger** | **禁止** | **最大4段**（既存の `nth-child(n+4)` でまとめる形を維持）。SP はさらに減らす | ○ 4段 |
| **常時動き続ける装飾** | **禁止** | 上の infinite loop と同じ。地紋・罫・生成ビジュアルのいずれも静止 | 無し |

**追加の禁止**

- **動きによって初めて情報が表示される設計**
- **新しい `@keyframes`**（承認なしに追加しない）
- **新しい時間の値**（`--m-fast` / `--m-rise` / `--m-peak` の3つを超えない）
- **GSAP などのアニメーションライブラリ**
- **`animation` の一括指定**（D-295）
- **AI に数値を選ばせること**（duration / delay / easing / distance）

## O. 実装責務

| 層 | 決めること | 決めてはいけないこと |
| --- | --- | --- |
| **Motion Language（TypeScript）** | 会社データから、**どの節をどの拍にするか**。有限の語彙だけ | 数値・CSS・HTML |
| **CSS** | **どう動くか**。`@keyframes` と `animation-*` | 何を動かすか（節の選択） |

`<html>` の `data-motion` は強さ（どの拍を使ってよいか）、帯の `data-motion-beat` は拍。
**属性を増やすほど、CSS と TS に同じ表が2つできる**（D-197）。

### 決定性

1. **乱数・時刻を使わない。** 同じ `project.json` なら同じ拍になる
2. **ビルド中に AI / API を呼ばない**
3. **同じ入力で2回計算して完全一致すること**を検査で固定する
4. `projectHashOf` に Motion Language を**数えさせない**（D-369 と同じ罠）

### AI の権限

| 選んでよい | 触れない |
| --- | --- |
| 拍（`still` / `settle` / `open` / `peak`） | CSS・JS・HTML |
| 強さ（`none` / `subtle` / `standard`） | 任意の数値 |
| 軸（`settle` / `sequence` / `arrive` / `emerge` / `none`） | 新しい `@keyframes` |

**語彙外の値は読み込みで落とす**（`assertLibrary` / `assertGenerated` と同じ思想）。

## Q1. Motion Language を実装した結果、98万円の商品に近づく根拠

**根拠は「動きが増えるから」ではない。「読む順序が設計されるから」である。**

| 変わること | なぜ体験の価値になるか | 測れるか |
| --- | --- | --- |
| **山が山に見える** | いま5つの帯が同じ動きをしていて、**どれが本題か画面から分からない。** 山だけ長い範囲で現れれば、スクロールしただけで「ここが本題」が伝わる | ○ 山とそれ以外の `animation-range` の差 |
| **間ができる** | `still` の節が、次の山を山にする。**間は、動きを足しても作れない。止めることでしか作れない** | ○ 動く節の数（5 → 3） |
| **並びに意味が出る** | 設備・沿革・工程が順に現れると、「これらは同じ仲間で、この順序に意味がある」が読む前に伝わる | ○ stagger が当たる節の数 |
| **会社ごとに違って見える** | いまは**型が同じなら動きも完全に同じ。** 勝ち筋から拍を決めれば、精度の会社と職人の会社で速さと間が変わる | ○ 2社の拍の並びが一致しないこと |
| **ページによって濃さが変わる** | トップは濃く、会社概要は薄く。**探しに来た人を動きで邪魔しない**のも体験設計である | ○ ページごとの動く節の数 |

**「98万円らしさ」を派手さで作らない理由**

読み手は調達担当者と設計者である。**この人たちが高いと感じるのは、演出ではなく、
探しているものがすぐ見つかることと、書いてある内容が信用できることである。**
動きの役割は、そこに至る**順序を整えること**に限られる。

**したがって、この設計で動きは「増えない」。むしろトップページでは 5節 → 3節に減る。**
増えるのは**差**である。

## Q2. Motion だけでは解決できない可能性がある問題

**正直に言うと、いまの「静的に見える」の原因は、Motion より外側に多くある。**

### ① 写真が1枚も無い（最大の要因）

**サイト全体の `<img>` タグは 0 個である。** 実写がゼロ。
画面にある画像は、生成ビジュアル4枚（`opacity .5`、その上に `--asset-veil: .72` の覆い）だけ。

- `kobo-reveal`（覆いが外れる）は**当たる対象が存在しない**
- `analysis.hasRealPhotos` が false なので、**写真を使う山も選ばれない**
- **これは Motion では絶対に埋められない。** 撮影が要る

### ② ページが短い

`equipment` 1.7画面 ／ `recruit` 1.5画面（PC）。
**時間の構成を作る土台が無い。** 拍を刻む余地が無い。
→ 情報量（ページ構成・原稿）の問題

### ③ 山がいつも先頭にある

13ページ中11ページで、山が**最初の帯**。
ご指示の「静→動→静→ピーク→静」という**上り坂は、いまのページ構成からは作れない。**
作れるのは「山 → 間 → 弱動 → 間 → 準山 → 静」という下り坂である。
→ 山を後ろに置くかは `visual.ts` の**ページ構成の判断**であって、Motion の仕事ではない

### ④ 工程モチーフが出ていない

`data-motif="process"` が 0。`kobo-grow` に当たる対象が無い。
→ モチーフは「聞き取りに裏づけのあるものだけ」敷く規則（docs/31）。
**聞き取りの中身の問題**であって、Motion の問題ではない

### ⑤ 生成ビジュアルが薄い

PC で `--asset-strength: .5`、その上に `--asset-veil: .72` の覆い。
**動かしても見えないものは、動かしても見えない。**
→ 濃さの判断は第9段階④の話。**社長の承認なしに変えない**

### ⑥ hero が最も長く見られるのに、情報量が少ない

hero は `.band` ではないので動きが当たらないが、**動かせば良くなるわけではない。**
SP では `.spec-first` の白いカードが帯の大半を占め、生成ビジュアルがほとんど見えない。
→ **ページ構造の問題**（以前から残タスク）

### ⑦ 文字組・余白

「完成感」は、行間・字間・見出しの階段・余白の呼吸で作られる部分が大きい。
→ 第7段階（docs/34）の続き。**モバイルの文字階段（D-348）が未着手のまま**

### まとめ

| 課題 | Motion で解決できるか |
| --- | --- |
| どこが本題か分からない | **○ できる**（山を山に見せる） |
| 全部が同じに見える／リズムが無い | **○ できる**（拍を作る・止める節を作る） |
| 会社ごとの違いが出ない | **○ できる**（勝ち筋から拍を決める） |
| 情報の順序・関係が読めない | **○ できる**（stagger を意味のある並びにだけ） |
| 写真が無い | **× できない**（撮影） |
| ページが短い・薄い | **× できない**（原稿・構成） |
| 山の位置 | **× できない**（`visual.ts` の構成判断） |
| 文字組・余白の完成感 | **× できない**（第7段階） |

**Motion Language は、この7項目のうち4項目に効く。**
残る3項目は Motion では動かない。**「動きを足せば98万円に見える」という前提は採らない。**
