# 自社ツール「KOBO」設計書

作成: 2026-09-12 / 仮称: KOBO（工房）／ 状態: **設計レビュー待ち**
※ ツール名は仮。屋号が決まったら合わせて見直す。

---

## 1. 何を作るのか

**ヒアリングフォームに入力 → 送信 → Webサイトが生成される、自社専用の制作基盤。**

```
┌────────────────────────────────────────────────────┐
│ ① ヒアリング入力（対面・その場で埋める）              │
│    取材台本(docs/06)の6ブロックに対応したフォーム      │
└──────────────────┬─────────────────────────────────┘
                   │ project.json（構造化された案件データ）
                   ▼
┌────────────────────────────────────────────────────┐
│ ② 生成                                              │
│    a. ページ構成の決定（案件の目的に応じて）           │
│    b. 全ページの原稿生成（Claude API）                │
│    c. Astro テンプレートへ流し込み                    │
└──────────────────┬─────────────────────────────────┘
                   ▼
┌────────────────────────────────────────────────────┐
│ ③ レビュー・調整（ここは必ず人間が通る）              │
│    プレビュー → 部分的に再生成 → 手直し               │
└──────────────────┬─────────────────────────────────┘
                   ▼
┌────────────────────────────────────────────────────┐
│ ④ 公開（Cloudflare Pages へデプロイ）                │
└────────────────────────────────────────────────────┘
```

### 重要な設計上の制約：送信ボタンを押すのは我々

顧客はフォームに入力するが、**生成を実行するのは契約後に案件を受領した我々。**
顧客が直接生成できてしまうと、品質保証ができず、契約前に成果物が渡ってしまう。

さらに **③のレビュー工程は絶対に飛ばさない。** 生成されたものをそのまま納品しない。
生成物はあくまで「原稿の第1稿」であり、商品は最終的に人が検収したもの。ここを崩すと品質が事故る。

### 取材台本との関係（一見矛盾する点の整理）

`06-取材台本.md` に **「記入式のヒアリングシートは絶対に送らない」** と書いた。これと矛盾しないか、を明確にしておく。

> **矛盾しない。** ダメなのは「送りつけて顧客に書かせる」こと。
> **対面で我々が聞きながら埋めるのは、取材の構造化であって、顧客の作業ではない。**

顧客の作業時間は増えない（提案書で約束した4.5時間は守られる）。
むしろフォームがあることで、取材の抜け漏れがなくなり、取材品質が属人化しなくなる。

**したがって、KOBOのフォームは `06-取材台本.md` の構造をそのまま実装したものになる。** 台本が仕様書。

## 2. なぜ作るのか（投資判断）

`02-サービス設計_v0.md` で「2件目以降の原価を下げられるかどうかで、この事業の利益率が決まる」と書いた。KOBOがその実装。

| | ツールなし | KOBOあり |
|---|---|---|
| 原稿執筆 | 案件あたり15〜20時間 | 生成2時間＋推敲4時間 |
| ページ組み | 案件あたり10時間 | 自動 |
| 3件目以降の実工数 | 初回とほぼ同じ | **初回比50%以下** |

**週15時間という制約下では、制作工数の削減が直接「営業に使える時間」になる。**
KOBOは制作ツールであると同時に、**営業時間を捻出するための投資**。

## 3. スコープ（作らないものを先に決める）

自社ツール、利用者は1人。**過剰に作ると、ツールの保守が本業を圧迫する。**

### v1 で作るもの

- ヒアリングフォーム（ローカルで動くWeb UI）
- 案件データの保存（プロジェクトごとのJSONファイル）
- 原稿生成（Claude API）
- Astro テンプレートへの流し込みとビルド
- プレビュー
- Cloudflare Pages へのデプロイ

### v1 で作らないもの

| 作らないもの | 理由 |
|---|---|
| ユーザー認証・マルチユーザー | 使うのは1人 |
| クラウドホスティング | ローカル実行で足りる。工場のネットは不安定なので、むしろオフラインで動くほうが良い |
| 顧客向けの編集画面 | 更新は保守契約で我々が代行する方針（`10` 第1章） |
| デザインのカスタマイズUI | テンプレートを直接編集すればよい |
| 課金・請求機能 | 会計ソフトでやる |
| WYSIWYGエディタ | 原稿はMarkdownで十分 |

> **「後で必要になるかも」で作らない。** 実案件で3回困ったら作る。

## 4. 技術構成

| レイヤー | 採用 | 理由 |
|---|---|---|
| ツール本体 | Next.js（ローカル実行） | フォームUIと生成APIを1つで賄える |
| 案件データ | ファイルシステム上のJSON | DBを立てない。Git管理でき、バックアップが自明 |
| 原稿生成 | Claude API | |
| サイト生成 | Astro | 静的出力。テンプレートは案件横断で共有 |
| デプロイ | wrangler（Cloudflare Pages） | CLIから叩ける |

### ディレクトリ構成

```
tool/
  app/              Next.js（フォームUI + 生成API）
  lib/
    schema.ts       ヒアリング項目の定義（単一の正）
    generate/       原稿生成のプロンプトとパイプライン
    deploy.ts       Cloudflare Pages へのデプロイ
  templates/
    manufacturing/  製造業向け Astro テンプレート
  projects/
    {{案件ID}}/
      project.json  ヒアリング結果
      draft/        生成された原稿（Markdown）
      site/         Astro プロジェクト
      assets/       写真
```

> **`lib/schema.ts` を単一の正とする。** フォームUI・バリデーション・生成プロンプト・テンプレートの型が、すべてここから導出される。仕様が二重管理になった瞬間に壊れ始める。

## 5. 生成されるサイトの構成

案件データの「サイトの目的」に応じて、生成するページを出し分ける。

| ページ | 条件 | 主な出典（ヒアリングのブロック） |
|---|---|---|
| トップ | 常に | 全体 |
| 会社概要・沿革 | 常に | ブロック1 |
| 強み・技術 | 常に | ブロック3（強みの質問群） |
| **対応可能範囲**（材質・サイズ・精度・ロットの表） | 常に | ブロック3 |
| **設備一覧**（メーカー・型番・台数） | 常に | ブロック3 |
| **加工事例**（1事例1ページ） | 事例が1件以上 | ブロック4 |
| 採用情報 | 目的に「採用」を含む場合 | ブロック5 |
| 代表挨拶 | 目的に「採用」or「信用構築」 | ブロック5 |
| お問い合わせ | 常に | — |

> **「対応可能範囲」と「設備一覧」は必ず作る。** BtoB製造業の検索は「材質×加工法×条件」と「設備型番」で行われる（`06` 第3ブロック）。この2ページがSEOの本体であり、多くの競合サイトに存在しない。

## 6. 原稿生成の方針

### 一度に全部生成しない

ページ単位でプロンプトを分ける。理由：

- 長文一括生成は品質が落ち、事実の混入（hallucination）が起きやすい
- 部分的な再生成ができないと、1箇所直すたびに全部作り直しになる

### 事実の捏造を絶対に防ぐ

**製造業の技術情報で嘘を書くと、信用を失うだけでなく取引事故になる。**

生成パイプラインに以下を組み込む：

1. **ヒアリングデータにない数値・型番・認証名は、生成に使わせない**（プロンプトで明示的に禁止）
2. 生成後、**原稿に現れる全ての数値・固有名詞を project.json と機械的に突き合わせ、出典のないものを検出して警告**
3. 曖昧な箇所は `{{要確認}}` マーカーを残す。人間が埋めるまでビルドを通さない

> ここは機能ではなく**安全装置**。v1から必ず入れる。

### 文体

- 製造業の調達担当者・技術者が読む前提。過度な形容を避け、具体の数字で書く
- 「高品質」「豊富な実績」といった無内容な表現を禁止語として定義し、生成後に検出する

## 7. 開発フェーズ

| 段階 | 内容 | 完了条件 |
|---|---|---|
| **v0.1** | `schema.ts` の確定とフォームUI | 実際の取材でフォームが使える |
| **v0.2** | 原稿生成パイプライン＋事実検証 | 1案件分の原稿が生成できる |
| **v0.3** | Astro テンプレート（製造業向け） | 生成原稿からサイトがビルドできる |
| **v0.4** | デプロイ＋フォーム＋解析の組み込み | Cloudflare Pages に公開できる |
| **v1.0** | 監視・月次レポート生成 | 保守契約の運用が自動で回る |

### 開発の順番について（社長判断）

**v0.1（フォーム）を最優先で作る。**

理由：自社サイトより先。フォームさえあれば、**テンプレートや生成が未完成でも取材に出られる。**
営業を止めないことが最優先で、生成部分は最初の1件を手作業で作りながら並行開発すればよい。

> 1件目は手作業で作る前提で進める。**1件目をツールで作ろうとすると、ツールが完成するまで営業できなくなる。** これは順番を間違えると致命的。
