# デザイン調査 — BtoB中小製造業サイトの「型」

調査日: 2026-09-13 / 目的: `tool/lib/theme.ts` の軸を増やすための材料集め
対象: 日本のBtoB中小製造業・町工場・金属加工会社のホームページ

---

## 0. この調査の限界（先に書く）

**実サイトを1件も直接開けていない。** この環境のネットワークは外向きが遮断されており、
WebFetch も `curl` も、試した企業サイト・記事サイトのすべてで失敗した。

| 手段 | 結果 |
|---|---|
| WebFetch（企業サイト8ドメイン） | 全滅（`EGRESS_BLOCKED`、1件はDNS解決失敗） |
| WebFetch（制作会社のまとめ記事 4ドメイン） | 全滅（`EGRESS_BLOCKED`） |
| `curl`（直接） | `CONNECT tunnel failed, 403` |
| WebSearch | **これだけ通った** |

したがって以下の観察は、**すべて検索結果の要約（=制作会社のまとめ記事を第三者が要約したもの）からの二次情報**である。
HTML/CSS を読んで確かめた事実は**ゼロ件**。色の16進値、フォントの指定、罫線の太さ、
セクションの実装方法（`border` か `background` か）といった**実装レベルの事実は一切取れていない。**

**このため「何サイト中いくつ」は、本来の意味では書けない。**
代わりに本文では **「収集した要約テキスト中で、その特徴に言及された記述が何件あったか」** を書く。
記述件数であって、母集団に対する比率ではない。**これを比率として読まないこと。**
数えていない印象は「印象」と明記する。

> この章は残しておくこと。後で読んだ人が「10サイト見た結果」と誤解すると、
> 根拠のない軸をテンプレートに入れる判断につながる。

## 2. 観点ごとの観察結果

**再掲: 以下の「◯件」は、収集した検索要約テキスト中の言及件数。サイト母数に対する比率ではない。**

### 2-1. ファーストビューの型

言及から拾えた型は3つ。

| 型 | 言及 | 中身 |
|---|---|---|
| **キャッチコピー先行**（文字が主役、背景に写真や動き） | 4件 | 「会社の革新性と独自性を象徴するコピー」「創業背景をシンプルに記す」「80年の歩みがつなぐ未来へ」（名古屋工業）「得意領域を明確に配置」（旭スプリング製作所） |
| **写真・映像で押す**（全面写真／工場内観の動画） | 3件 | 「写真をふんだんに使ったレイアウト」（特殊鋼卸売）「工場の内観を中心に映した動画が規模の大きさを印象づける」（多田精機）「使用シーンの写真を多く活用」 |
| **製品カテゴリ／モチーフを即出し** | 2件 | 「製品カテゴリーが分かりやすく配置され、何を扱うか一目で分かる」「ねじの画像を背景・コピーに配置」（曙螺子工業） |

**スペック表（対応材質・精度）をファーストビューに即出しする型は、言及が0件だった。**
ただしこれは「無い」ことの証明ではない。まとめ記事は見栄えのよいサイトを選ぶ性質があり、
スペック即出し型は記事に選ばれにくいという偏りが考えられる（**推測**）。

一方で、記事側の「べき論」としては**スペックを数字で出せ**という主張が繰り返し出てくる：
「『高精度』『高品質』といった主観的表現は避け、具体的な数字で示す」「型番まで正確に記載する」
（TMCデジタル・設備紹介ページ記事、言及2件）。
→ **「言われていること（数字を出せ）」と「まとめ記事で褒められているもの（写真とコピー）」がずれている。**
我々の顧客（写真が揃わない町工場）にとっては前者の型が要る、というのが本調査の一番大きい示唆。

### 2-2. ヘッダーの型

- **ヘッダーに問い合わせボタンを置く**: 言及3件。「どのページでも共通して表示されるヘッダーやフッターに、フォームに誘導するボタンを配置」「ヘッダーやグローバルメニューなど目に付きやすい位置」「問い合わせボタンが目立つ色・他ボタンと異なるデザイン」。
- **ファーストビュー内に電話番号＋受付時間**: 言及1件（「ファーストビューの目立つ場所に電話番号と受付時間が記され、最下部にも電話番号とメールフォームへのリンク」）。
- **ヘッダー固定（追従）＋カルーセルとメニューの連動**: 言及1件。
- **CTAを行動段階で分ける**（「お問い合わせ」「見積」「カタログ」を並べる）: 言及1件。

ロゴの位置（左寄せか中央か）について明示した記述は**0件**。取れなかった。
中央ロゴ型がどれくらいあるかは不明。

→ 我々のテンプレートは既に「ロゴ左＋電話＋ボタン、ナビは下段」で、
D-060（電話を全ページに）とも一致する。**ここは観察と矛盾しない。**

### 2-3. 見出しの飾り方

製造業に限定した記述は薄く、一般的な見出しデザイン記事からの列挙が主：
「下線のみ」「左側に横ラインを入れたもの」「短いライン付きの中央寄せ」「英語＋下線」
「英語フォントを装飾っぽく配置」「装飾のように背景に透かせたデザイン」（言及は記事3本にまたがる）。

製造業サイト個別で拾えたのは：
- 「セクションごとに見出しを大きく分け、余白を活かす」（イーグルブルグマン、1件）
- 「セクションの見出しに明朝体を使う」（和風デザイン記事、1件）

**英字の添え字（eyebrow）が製造業で標準かどうかは確認できなかった。**
一般Webデザインの定番としては複数記事で挙がっている（3件）が、それが製造業でどの程度使われているかは不明。

### 2-4. セクションの区切り方

- **斜めに区切る**: 言及2件（神明電機「TOPページで斜めのラインを取り入れて動きを演出」、特殊鋼卸売「斜めに区切るようなデザイン」）。
- **背景色＋余白で分ける**: 言及1件（「背景色を工夫することで、余白と合わせてセクション分けをわかりやすくする」）。
- **余白のみ・大きな見出しで分ける**: 言及1件（イーグルブルグマン）。
- 罫線1本で区切る型への明示的な言及: **0件**（我々のテンプレートの現状はこれ）。

注意すべき記述（実装ガイド側）: 「波形や斜めラインは1ページに1〜2箇所にとどめ、
複数の区切り手法を多用すると視線が分散するため、視覚効果より情報設計を優先する」。

### 2-5. 表（対応材質・設備一覧）の罫線

**罫線の引き方そのものを記述した資料は見つからなかった（0件）。** ここは完全に取れていない。

取れたのは「表を置け」という設計側の話のみ：
- 「ページ下部に一覧表を配置すると設備の全体像が明らかになり、購買・設計・研究開発の担当者が比較検討しやすい」（1件）
- 「保有設備の一覧や台数、特許技術、ISO認証といった客観的データは、発注側にとって重要な選定基準」（1件）
- 「型番まで正確に記載することが検索経由の流入を増やす観点でも有効」（1件）
- 「加工条件・寸法公差・ワークの材質など、閲覧者が参考にできる情報を掲載」（1件）

→ **表は「あるか無いか」が論点で、罫線の様式は誰も語っていない。**
軸として足す価値はあるが、根拠は「観察」ではなく「一般的なCSSの選択肢」である。正直にそう書く。

### 2-6. 配色

言及された色（企業サイト単位の記述、計7件）：

| 色 | 件数 | 文脈 |
|---|---|---|
| 青・ネイビー | 3 | 神明電機「各装飾にブルーが積極的に取り入れられ、誠実さが伝わる」／「水色と白で清潔感」（金属加工）／特殊鋼卸売「ネイビーとピンクのコントラスト」 |
| 白・グレー基調 | 2 | 自動水栓メーカー「白やグレー基調で自社商品が映える」／グレー基調の記事1本 |
| 緑 | 1 | 珪砂・セメント資材「優しいトーンの緑で親しみやすく」 |
| 差し色としてのピンク | 1 | 特殊鋼卸売（ネイビー×ピンク） |

→ 青系が最多（3/7件）というのは**言及数としては**そう言える。
「製造業は青が多い」という通説と矛盾しないが、**これで裏付けたとは言えない**（母集団が偏っている）。
`theme.ts` の既定が「藍」であることは、少なくとも否定されない。

**差し色（アクセント）の使い方**で拾えた唯一の具体例が「ネイビー×ピンク」で、
**寒色ベースに1色だけ暖色を刺して締める**という型。件数1件なので型として弱い。

### 2-7. 書体

- 「BtoBサイトではフォント選びで信頼感・安心感が最も重要」（1件）
- 「BtoB商材は検討期間が長くサイト内の文章をじっくり読まれるため、太さやバランスの整ったWebフォントは読むストレスを軽減し、離脱率低下・滞在時間延長に寄与する」（1件）
- 「Webフォントで企業の世界観をコントロールできる」（1件）
- 「セクション見出しに明朝体を使うと洗練された雰囲気になる」（和風デザイン文脈、1件）
- **Noto Sans JP / 游ゴシック等の具体的な採用率データは見つからなかった**（検索側も「詳細なデータは含まれていません」と明示）。

→ 我々の FONTS（ゴシック／明朝／見出しだけ明朝／丸ゴシック／Noto）は、
**言及された選択肢を概ね覆っている。書体軸を増やす必要は薄い。**

### 2-8. 写真が少ないサイトの間の持たせ方

これは一番役に立った観点。

- **図解・テクニカルイラストに置き換える**: 言及3件（「専門的な製品や技術をどう見せるかが重要で、テクニカルイラスト制作でサイト内で使いやすい図解素材を作る」「製品の基本情報や種類、動作をイラスト付きでまとめる」「複雑な装置も情報を整理して見やすいビジュアルにする」）。
- **情報量そのもので持たせる**: 三和メッキ工業。「メッキ辞典と言えるほどの情報量、めっきQ&Aは常時4,000〜6,000件」。
- **加工前／加工後の写真をデータベース化**: 同社。**撮影の手間が小さい写真（部品の前後）を大量に積む**という型。設備写真や現場写真より現実的。
- **数字で埋める**: 「実績や設備の情報を数字で紹介するコンテンツを設けることで、会社をより具体的に伝える」（1件）。
- **日本のBtoBサイトは縦長・情報量重視**（欧米はミニマル）という比較（1件）。→ **余白で持たせる欧米型は、日本のBtoB調達では必ずしも正解ではない。**

→ **写真0枚でも成立させる我々の前提（D-099）は、「情報量で持たせる」型として実在する。**
ただし実在例（三和メッキ）は**文字量が桁違い**で、90分取材で作れる量ではない。
そこを埋めるのが「表・数字・図解」になる、というのが結論。

## 3. `tool/lib/theme.ts` に足すべき軸の提案

現状は4軸（`palette` / `font` / `mood` / `layout`）。
提案は**優先度順**。各案に「どういう会社に向くか」「実装の重さ」を付ける。

実装の重さの定義:
- **軽**: `theme.ts` に値を足し、`themeVars()` にCSS変数を追加し、`site.css` にルールを足すだけ
- **中**: `<html>` の `data-*` 属性を1つ増やし、`site.css` にセレクタ分岐を足す（Astro は触らない）
- **重**: `Base.astro` / `index.astro` のマークアップ分岐が要る

---

### 提案1: `HEADINGS`（見出しの飾り方）— **最優先**

| id | label | 中身 |
|---|---|---|
| `plain` | 飾らない | 太字のみ。現状の `h2` |
| `rule-left` | 左に罫 | `border-left: 4px solid var(--accent)`。既に `.case-body h2` で使っている型を全体に |
| `underline` | 下線 | `border-bottom` を見出し幅で。太さは `--line-width` に連動 |
| `band` | 背景帯 | `background: var(--accent-soft)` + 左罫。図面の表題欄に近い硬さが出る |

**どういう会社に向くか**: 写真が少なく、文字と表だけのページが続く会社ほど効く。
見出しに手掛かりが無いと、縦に長いページで「今どこか」が分からなくなる（写真0枚前提の副作用）。
`plain` は写真が多い会社、`band` は仕様書的に読ませたい会社。

**実装の重さ: 軽〜中。** `data-heading` 属性1つと `site.css` の4ブロックで済む。
Astro のマークアップ変更は不要。`.case-body h2` の既存ハードコードをこの軸に吸収する整理が要る。

**根拠の強さ**: 中。見出し装飾の選択肢自体は複数記事で列挙されている（3件）が、
製造業サイトでの分布は測れていない。**「飾りの選択肢がゼロ」という現状が問題である**、という論拠のほうが強い。

---

### 提案2: `SECTIONS`（セクションの区切り方）— **最優先**

| id | label | 中身 |
|---|---|---|
| `line` | 罫線 | 現状。`.section + .section { border-top }` |
| `alt` | 背景色の交互 | 偶数セクションを `--bg-soft` に。全幅の帯になる |
| `space` | 余白のみ | 罫線を消し、`--section` を増やす |

**どういう会社に向くか**:
- `line` = 情報密度が高い会社（表や一覧が多い）。区切りが細いので詰めて読める
- `alt` = セクション数が多い会社。写真が無くても画面にリズムが出る。**写真0枚のときの主力**
- `space` = ページ数が少なく、1ページの中身が短い会社。間延びに注意

**実装の重さ: 軽。** `.section:nth-of-type(even)` の背景切替だけ。
ただし `.section` が `.inner` の内側に padding を持つ構造なので、
`alt` では**背景が全幅に伸びること**を確認する必要がある（現状の `.section` は全幅なので問題ない見込み）。
`.page-head` と `.cta` が既に色付き帯なので、**それらと交互色がぶつからないか**だけ要確認。

**根拠の強さ**: 中。「背景色＋余白でセクションを分ける」への言及1件、
「余白と大きな見出しで分ける」1件。罫線型への言及は0件だが、これは記事が触れないだけと考えられる（**推測**）。

---

### 提案3: `TABLES`（表の罫線）— **推奨**

| id | label | 中身 |
|---|---|---|
| `grid` | 全部に罫 | 現状。図面・仕様書に近い |
| `rows` | 横罫だけ | 縦罫を消す。行数が多い設備一覧が読みやすい |
| `stripe` | 行の縞 | 罫線を薄くし、偶数行に `--bg-soft` |

**どういう会社に向くか**: 対応材質・設備一覧・公差表を**大きく載せる会社**ほど効く。
設備が30行あるページで全罫は目が滑る。逆に会社概要の2列表しか無い会社は `grid` のままでよい。

**実装の重さ: 軽。** `th, td` の `border` 指定を `data-table` で分岐するだけ。
**ただし注意が1つある**: `site.css` の `@media (max-width: 720px)` で
表を `display: block` の縦積みに作り替えている（219〜225行）。
`stripe` / `rows` は**この縦積みの見え方も併せて定義しないと、スマホで区切りが消える。**
そこだけ手当てが要るので、純粋な「軽」より少し手間がある。

**根拠の強さ: 弱い（正直に書く）。** 表の罫線様式を論じた資料は0件。
「設備一覧表を置け」「型番まで書け」という設計側の要請（言及4件）から、
**表が長くなることは確か**で、その帰結として罫線様式が効くだろう、という**推論**である。

### 提案4: `HERO`（ファーストビューの型）— **推奨、ただし `layout` の整理とセット**

現状 `LAYOUTS` は **ナビの置き方（standard/sidebar）と ヒーローの写真サイズ（wide）を1つの軸に混ぜている。**
`sidebar` かつ写真を大きく、が選べない。**ここは今の4軸の中で唯一はっきりした設計上の問題。**

`layout` から写真の話を切り出し、`hero` を独立させる案：

| id | label | 中身 | 向く会社 |
|---|---|---|---|
| `text` | 見出し先行 | 現状の `.hero`（h1＋lead＋facts）。写真なし | **写真が1枚も無い会社。既定にすべき** |
| `photo` | 写真を大きく | 現 `layout: wide` 相当 | 外観・現場の写真が良い会社 |
| `spec` | スペック即出し | h1 の直下に「対応材質／加工法／対応サイズ／精度」の表を置く | **技術取材が取れた会社。検索で拾われる本体をFVに出す** |
| `split` | 左に文字・右に写真 | 2カラム | 写真が1〜2枚だけある会社 |

**`spec` が本調査の一番の提案。** まとめ記事が褒めるのは写真とコピーだが、
設備紹介ページの記事が繰り返し言うのは「主観的表現を避け数字で示せ」「型番まで書け」。
**写真が揃わない町工場が勝てるのは後者側で、それをFVに置く型を我々は持っていない。**
docs/06 が「材質×加工法×条件、設備型番」をBtoB製造業の検索の本体と書いているのと一致する。

**実装の重さ: 重。** `index.astro` のヒーロー部分にマークアップ分岐が要る。
`spec` は表示だけでなく**データ（材質・加工法・サイズ・精度）が揃っている前提**なので、
揃っていない案件で `spec` を選ぶと空欄の表が出る。**KOBO側で選択可否を出し分ける必要がある。**
（docs/15 の通り、社長だけの取材ではこの4項目が全部空欄になる。）

**根拠の強さ**: FVの型が分かれること自体は言及9件（キャッチ先行4/写真3/カテゴリ即出し2）で確か。
`spec` 型の実在は**確認できていない（言及0件）**。設計側の要請からの構成であり、**これは提案であって観察ではない。**

### 提案5: `DENSITY`（情報の密度）— **`mood` の拡張として推奨**

新軸を足さず、既存の `Mood` に2つフィールドを足す案：

```
fontSize:  "16px" | "17px" | "18px"
maxWidth:  "960px" | "1040px" | "1120px"
```

**どういう会社に向くか**: 「日本のBtoBサイトは情報量重視で縦長」（言及1件）に対し、
**表と数字が多い会社は詰めたほうが読める。** 逆に高齢の経営者が自分で確認する場面を考えると、
`yawaraka` は文字も大きいほうが筋が通る。現状 `mood` は角丸・行間・罫の太さしか動かしておらず、
**文字サイズと本文幅という、印象への寄与が大きい2つが固定されている。**

**実装の重さ: 軽。** `themeVars()` に2行、`site.css` の `body { font-size }` と `--max` を変数化するだけ。
**新しい軸を増やさずに見た目の差が広がるので、費用対効果が一番高い。**

### 提案6: `ACCENT_USE`（アクセントの面積）— 中優先

| id | label | 中身 |
|---|---|---|
| `line` | 締めに細く | 現状。リンク・左罫・ボタンだけに使う |
| `band` | 帯で使う | ヘッダー下のナビ、`.page-head` をアクセント色ベタに |
| `invert` | 濃色ヘッダー | ヘッダー全体を `--accent-dark` に、文字を白に |

**どういう会社に向くか**: `invert` は**ロゴ画像が無い会社**に効く（社名テキストが白抜きで載るだけで形になる）。
`band` は色を1色しか使わない会社。`line` は写真が多い会社（色が写真とぶつからない）。

**実装の重さ: 中。** CSS変数だけでは足りず、`.site-header` / `.site-nav` / `.logo` / `.tel` の
文字色を `data-accent` で反転させるセレクタ群が要る。**ロゴ画像がある案件では白抜きにできない**ので、
ロゴ画像の有無で `invert` を選べなくする分岐が要る（`Base.astro` の `photoOf("ロゴ")` を見て判定）。

**根拠の強さ: 弱い。** 濃色ヘッダーへの明示的な言及は0件。
「差し色を効かせて締める」型は特殊鋼卸売の1件のみ。**実サイトを見られなかったせいで一番確度が低い提案。**

## 4. 足さないほうがよいと判断したもの

### 4-1. 斜め・波形のセクション区切り（`clip-path` / `skew`）

言及は2件あり（神明電機、特殊鋼卸売）、実在する型ではある。だが足さない。

- 収集した実装ガイド自身が「1ページに1〜2箇所にとどめよ」「多用すると視線が分散する。
  視覚効果より情報設計を優先せよ」と書いている。**セクション数が多い我々のテンプレートとは相性が悪い。**
- `site.css` は `@media print` で印刷を想定している。**斜め背景は印刷で崩れるか、インクを食う。**
  中小製造業は提案書やサイトを印刷して社内に回すことがある（docs/06 が現行サイトの印刷を前提にしている）。
- 全幅の斜めはスマホ幅で角度が破綻しやすく、案件ごとの検証コストがテンプレート1本という方針（D-096）に合わない。

### 4-2. ダークテーマ／配色の明暗反転

言及0件。BtoB調達担当者が昼間のオフィスで見る前提で、必要性の根拠が無い。
`PALETTES` の構造（`bg` が白前提、`accentSoft` が淡色前提）を全部作り直す必要があり、**割に合わない。**

### 4-3. カルーセル・スライダー・動画

言及はある（多田精機の工場内観動画、カルーセルとメニューの連動）。だが足さない。
**写真0枚でも成立させるという前提（D-099）と正面から矛盾する。**
写真3枚しか無い会社でカルーセルを回すと、素材の少なさがかえって露呈する。
動画は撮影費と納期4週間に載らない。

### 4-4. 書体の追加

`FONTS` は既に5種あり、収集した言及（ゴシック／明朝／Webフォント／信頼感）を覆っている。
**Webフォントを増やすほど表示が遅くなり、Googleへの依存が増える**（theme.ts のコメント通り）。
唯一検討の余地があるのは **Noto Serif JP（明朝のWebフォント）** で、
「見出しに明朝で洗練」（言及1件）を端末差なく出せる。ただし**明朝は既に3択ある**ので、急がない。

### 4-5. 英字の添え字（eyebrow）を独立した軸にすること

見出しの型（提案1）の1バリエーションとしては考えられるが、**軸として独立させない。**
理由は実装ではなくデータ側：**英語の見出し語（"PRODUCTS" "ABOUT US"）を誰が決めるのか。**
90分取材でそれを聞く時間は無く、我々が勝手に付けると英語が間違ったまま納品される危険がある。
自動生成すると「CASE」「WORKS」のような当たり障りのない語しか出ず、飾りとして機能しない。
**データが取れない飾りは軸にしない。**

### 4-6. サイドバーの左右反転、メガメニュー

言及0件。ページ数が10〜15の会社にメガメニューは不要。
`sidebar` が既にあるので、これ以上ナビの型は増やさない。

## 5. まとめ（優先順）

1. **`mood` に `fontSize` / `maxWidth` を足す** — 軽い。新軸ゼロで見た目の幅が一番増える
2. **`SECTIONS`（罫線／交互背景／余白）** — 軽い。写真0枚のときの主力
3. **`HEADINGS`（無装飾／左罫／下線／背景帯）** — 軽〜中。既存のハードコードを吸収できる
4. **`TABLES`（全罫／横罫／縞）** — 軽。ただしスマホ縦積みの手当てが要る。根拠は推論
5. **`HERO` を `layout` から分離し、`spec`（スペック即出し）を新設** — 重い。**が、商品の核心に一番近い**
6. `ACCENT_USE`（アクセントの面積） — 中。根拠が一番弱いので後回し

**足さない**: 斜め区切り、ダークテーマ、カルーセル・動画、書体の追加、英字添え字の独立軸、メガメニュー
