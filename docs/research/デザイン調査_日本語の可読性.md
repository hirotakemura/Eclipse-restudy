## 1. 調べたこと

### 1-1. 文字サイズ・行間・1行の文字数

#### 文字サイズ

- **【検索要約】** Web本文の一般的な標準は 14〜16px。Google は 16px を推奨しており、16px 未満はモバイルフレンドリーでないと判定されうる、との記述。
  出典（原典未読）: [ジーピーオンライン](https://www.gpol.co.jp/blog/292/) / [Web広島](https://web-hiroshima.com/blog/seo/4218/)
- **【検索要約】** **高齢者向けサイトでは本文 16〜18px 以上、見出し 20px 以上が推奨**、17〜18px が望ましい、との記述。
  出典（原典未読）: [Tasou](https://tasou.jp/blog/elderly-welfare-usability/) / [神戸ソフト](https://kobesoft.co.jp/design/kobe-homepages/font-readability/)
- **【検索要約】** 日本語は欧文より画数が多く、同じ 16px でも小さく感じられるため、実務では +1〜2px 見込むのが一般的、との記述。
  出典（原典未読）: [ジーピーオンライン](https://www.gpol.co.jp/blog/292/)
- **【未確認】** 公的な一次規格としては **JIS S 0032:2003「高齢者・障害者配慮設計指針―視覚表示物―日本語文字の最小可読文字サイズ推定方法」** が存在する。これは「年齢・視力・視距離・輝度から、日本語1文字が読める最小サイズを推定する式」を定めたもので、**本件にいちばん近い一次規格。** ただし **規格本文は有料頒布で、今回入手できなかった。推定式の係数も、そこから出る具体的な pt 値も未確認。**
  所在: [日本規格協会](https://webdesk.jsa.or.jp/books/W11M0090/index/?bunsyo_id=JIS+S+0032:2003) / [国立国会図書館](https://ndlsearch.ndl.go.jp/books/R100000002-I000004258170)
  → **この規格を買うのが、この論点にケリをつける唯一の確実な手段。** 現状「17px が良い」は実務記事どまりで、裏は取れていない。

#### 行間（line-height）

- **【検索要約】** WCAG 2.1/2.2 の達成基準 **1.4.12 Text Spacing（レベルAA）** は、利用者が **行間を文字サイズの1.5倍**、段落間を2倍、字間を0.12倍、語間を0.16倍に上書きしても、**内容や機能が失われないこと**を求める。
  出典（原典未読）: [W3C 1.4.12](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html) / [Deque](https://dequeuniversity.com/resources/wcag2.1/1.4.12-text-spacing)
  **重要な注意：1.4.12 は「1.5 で組め」という規定ではない。「利用者が 1.5 に変えても壊れるな」という規定。** ここを取り違えている解説記事が多い。自分たちの `--leading` が 1.5 を超えていること自体は、1.4.12 の適合とは関係がない。
- **【検索要約】** 実務の目安として、行間は文字サイズの1.5倍以上、**日本語では 1.7〜1.9 程度がより読みやすい**、との記述。
  出典（原典未読）: [神戸ソフト](https://kobesoft.co.jp/design/kobe-homepages/font-readability/) / [TANE-be](https://tane-be.co.jp/knowledge/web-design/2601/)

#### 1行の文字数（行長）

- **【検索要約】** 横書きで **1行 30〜40字**、広めに見て 15〜35字、という記述が複数。国立国語研究所・草島時介氏の実験で「横組30字・縦組25字がもっとも速く読める」とされる、との記述。
  出典（原典未読）: [アーティス](https://blog.asobou.co.jp/web/text-design02) / [ブックホン](https://www.book-hon.com/column/5521/) / [日経xTECH（遮断され未読）](https://xtech.nikkei.com/it/article/COLUMN/20080317/296389/)
- **【未確認】** 草島氏の実験の原典（発表年・掲載誌・被験者数・年齢層）は特定できなかった。**とくに「高齢者を対象にした行長の実験」は見つけられていない。** 30〜40字という数字は、高齢者向けの根拠としては裏が取れていない。
- **【検索要約】** 1行20〜29字にすると速く読める、という別方向の報告もある（[ナゾロジー](https://nazology.kusuguru.co.jp/archives/136891)）。**つまり実務記事の間でも一致していない。**

> **この節の結論：** 「1行30〜40字」は業界の通説であり、**高齢読者向けの一次的根拠はこの調査では取れていない。** ただし後述のとおり、現行実装は通説の範囲から**大きく外れて**おり（58.8字）、どの説を採っても外れている。そこは是正の根拠になる。

### 1-2. 和文書体の使い分け（ゴシック体と明朝体）

**【検索要約】**（出典: [ffont.jp](https://ffont.jp/collections/gothic-mincho-matome/) / [Edit Partners](https://www.edit-partners.jp/column/font) / [神楽坂エディターズ](https://kagurazaka-editors.jp/mincho-gothic-special/)。いずれも原典＝制作会社の解説記事であり、学術的根拠ではない）

| | 明朝体 | ゴシック体 |
|---|---|---|
| 得意 | **可読性**（長文を読み続ける） | **視認性**（ぱっと認識する、遠くから判別する） |
| 字画 | 横画が細く、縦画が太い。ウロコあり | 線幅が均一 |
| 紙での定番 | 書籍の本文 | 見出し、キャプション |
| Webでの定番 | ブランディング目的の見出し | **本文の標準** |
| 印象 | 伝統・格式・信頼・落ち着き | 現代的・明快・親しみ |

要点：

1. **Web本文はゴシック体が標準。** 理由は、ディスプレイの解像度では明朝体の**細い横画が表示しきれず、かえって読みにくくなる**から。
2. 高解像度ディスプレイ（Retina 等）が普及した近年は、ブランディング目的で本文に明朝体を使うサイトも増えている。
3. モバイル端末ではゴシック体が好まれる傾向。
4. 「見出しに明朝、本文にゴシック」は、格を出しつつ読みやすさを保つ定石の組み合わせ。

**【未確認】** 「高齢者にとって明朝体とゴシック体のどちらが読みやすいか」を直接比較した研究は、今回見つけられなかった。ただし上記1（細い横画が潰れる）は、**加齢によりコントラスト感度が落ちる読者に対して不利に働く**と推論できる。これは推論であって、測定された事実ではない。

### 1-3. Webフォントの代償と、日本語Webフォントのファイルサイズ

**この節は【実測】が取れた。この文書でいちばん確度が高い部分。**

`theme.ts` の `noto` が読み込んでいる URL を、実際に叩いて計測した。

```
https://fonts.googleapis.com/css2?family=Noto+Sans+JP:wght@400;600;700&display=swap
```

#### 実測結果

| 項目 | 実測値 |
|---|---|
| 返ってくる CSS のサイズ | **342,195 バイト（334 KB）** |
| `@font-face` 宣言の数 | **372個**（400/600/700 各124個） |
| 参照される woff2 の**実URL数** | **124個**（3ウェイトで完全に同一URL） |
| woff2 全124ファイルの合計 | **5,223,320 バイト = 4.98 MB** |
| 1ファイルの大きさ | 最小 8,232 B / 中央値 21,876 B / 最大 90,144 B |
| **製造業サイトの典型的な本文を表示するのに必要な実ダウンロード量** | **26ファイル・約 497 KB** |

補足（実測から分かったこと）：

- **Noto Sans JP はバリアブルフォントとして配信されており、400・600・700 の3ウェイトを指定しても実ファイルは同一。** つまり「ウェイトを3つ指定したから3倍重い」ということはない。`theme.ts` のウェイト指定は、この点では無駄になっていない。
- Google Fonts は `unicode-range` で124分割しており、**ページに出現した文字を含むチャンクだけが落ちてくる。** 全部落ちることはまずない。
- 497 KB という数字は、北九州のBtoB製造業を想定した本文（会社概要・設備一覧・材質・板厚・電話番号・ナビ項目など、約400字＋英数字）で計測した実測値。**ページの漢字の種類が増えれば増える。**
- **HTTPリクエストが26本増える**点も見落としてはいけない。サイズだけの問題ではない。

> 比較のため：この 497 KB は、**中小製造業のサイト1ページ分のHTMLとCSSを合わせたサイズより、はるかに大きい。** 「Webフォントを選ぶと表示が少し遅くなる」という `theme.ts` の注記は、**控えめすぎる。** 実態は「本文が出るまでに 0.5 MB を26本に分けて取りに行く」である。

#### ちらつき（FOUT / FOIT）

- **【検索要約】** `font-display` には block period（この間フォントが未ロードなら**不可視**でレンダリング＝FOIT）と swap period（この間は**代替フォント**でレンダリング＝FOUT）がある。
  - `block`: 短いブロック期間（**3秒が推奨**）＋無限のスワップ期間
  - `fallback`: きわめて短いブロック期間（**100ms以下が推奨**）＋短いスワップ期間（3秒推奨）
  - `swap`: ブロック期間0＋無限のスワップ期間 → **即座に代替フォントで表示し、あとから差し替わる（FOUT）**
  出典（原典未読）: [CSS Fonts Module Level 4](https://www.w3.org/TR/css-fonts-4/)
- **【検索要約】** `display=swap` は LCP（表示速度）には有利だが、**あとから Webフォントに差し替わる際に文字幅・字面が変わり、レイアウトシフト（CLS）を起こす。** 日本語フォントは代替（システムフォント）との字幅差が出やすい。
  出典（原典未読）: [Lighthouse font-display（遮断され未読）](https://developer.chrome.com/docs/lighthouse/performance/font-display) / [コリス](https://coliss.com/articles/build-websites/operation/work/optimizing-the-display-of-web-fonts.html)

`theme.ts` の `noto` は `&display=swap` を指定しているので、**この構成では FOIT（文字が消える）は起きず、FOUT（あとからガクッと切り替わる）が起きる。** 60代の読者にとって、読み始めた文章が途中で作り直されるのは、若い読者よりも負担が大きいと考えられる（**これは推論。測定した事実ではない**）。

### 1-4. 色のコントラスト比の基準

**【検索要約】**（W3C の原典 URL は示すが、**egress で遮断され直接読めていない。** 数値は検索結果要約に依拠）

| 達成基準 | レベル | 対象 | 必要比 |
|---|---|---|---|
| **1.4.3 Contrast (Minimum)** | AA | 通常のテキスト | **4.5:1** |
| 1.4.3 | AA | 大きなテキスト | **3:1** |
| **1.4.6 Contrast (Enhanced)** | AAA | 通常のテキスト | **7:1** |
| 1.4.6 | AAA | 大きなテキスト | **4.5:1** |
| **1.4.11 Non-text Contrast** | AA | UI部品・意味を持つ図形（ボタンの境界、フォーム枠、アイコン等）と隣接色 | **3:1** |

- **「大きなテキスト」の定義：18pt（= 24 CSS px）以上、または 14pt 太字（= 19 CSS px 太字）以上。**
- 装飾のみのテキスト、無効化されたUI部品のテキスト、ロゴタイプには 1.4.3 の要件は適用されない。
- **1.4.11 の 3:1 は閾値であり、丸めてはいけない**（2.999:1 は不適合）。

出典（いずれも原典未読）: [W3C 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) / [W3C 1.4.11](https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html) / [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/) / [Deque 1.4.11](https://dequeuniversity.com/resources/wcag2.1/1.4.11-non-text-contrast)

**【未確認】** 日本国内の規格は **JIS X 8341-3:2016**（WCAG 2.0 と一致）で、公的機関には総務省「みんなの公共サイト運用ガイドライン」が AA 準拠を求めている。**ただし総務省サイトも遮断され、ガイドライン本文を確認できていない。** また **JIS X 8341-3 は 2026年度に改正見込み**という記述があったが、これも未確認。
所在: [総務省ポータル（未読）](https://www.soumu.go.jp/info-accessibility-portal/webaccessibility/guideline/) / [みんなの公共サイト運用ガイドライン2024年版 PDF（未読）](https://www.soumu.go.jp/main_content/000945249.pdf)

> なお、BtoB中小製造業の民間サイトに **JIS X 8341-3 の法的な義務はない**（義務は公的機関）。ただし**調達担当者の勤務先が官公需に関わる場合、取引先サイトのアクセシビリティを見る可能性はある**。これは営業上の論点であって、法令上の論点ではない。

### 1-5. 高齢の利用者に配慮した配色で、避けるべき組み合わせ

**【検索要約】**（出典: [川崎市 カラーUDガイドライン PDF](https://www.city.kawasaki.jp/170/cmsfiles/contents/0000024/24002/cud_guide.pdf) / [情報管理 55(5) 307, J-STAGE](https://www.jstage.jst.go.jp/article/johokanri/55/5/55_307/_html/-char/ja/) / [デザインのコト](https://designk.jp/hard-to-recognize-to-senior) / [DSセルリア](https://selrea.co.jp/life/life65/)）

**機序：** 加齢により水晶体が黄変する。視界全体に黄〜茶のベールがかかった状態になり、**短波長（青系）の光が網膜に届きにくくなる。** 加えてコントラスト感度が落ちる。

#### 避けるべき組み合わせ

| 組み合わせ | 理由 |
|---|---|
| **青 × 黒** | 青が黒く沈んで見え、区別がつかない |
| **黄 × 白** | 黄が白く飛んで見え、区別がつかない |
| **寒色同士**（青×紫、青×緑 など） | 短波長側が潰れる |
| **暖色同士**（赤×オレンジ など） | 黄変ベールで差が縮む |
| **淡い色同士 / 明るい色同士 / 濃い色同士** | **明度・彩度が近い配色は総じて不可** |
| 青系の細い文字・細い罫線 | 黄変＋コントラスト感度低下の二重苦 |

#### 通りやすい組み合わせ

- 白 × 黒、白 × 濃緑、青 × 黄 のように**明度差の大きい配色**
- 赤・オレンジ・緑などの**鮮やかで濃い色**は、水晶体の黄変の影響を受けにくく認識しやすい

**【未確認】** 上記のうち「青×黒」「黄×白」は複数の日本語記事で一致しており通説と見てよいが、**具体的な明度差の閾値（何ポイント以上離せばよいか）を定めた一次規格（JIS S 0033 等）は入手できていない。** WCAG の 4.5:1 / 3:1 は色覚に配慮した輝度比の基準ではあるが、**「加齢による水晶体黄変」を直接モデル化したものではない。** つまり **WCAG AA を満たしていても、青×黒のような色相の問題は素通りする。** ここは数字だけでは守れない。

### 3-2. 1行の文字数 —— **これが最大の逸脱**

## 4. 足すべき選択肢の提案

### 4-1. 【最優先】本文の行長（measure）を絞る —— 選択肢ではなく既定の修正

**選択肢として増やすのではなく、既定を直すべき。** 行長58.8字は、どの説から見ても外れている。

案：`site.css` に本文用の幅を1つ足す。`--max`（1040px）は器のまま残し、散文にだけ効かせる。

```
--measure: 720px;   /* 17px × 約42字 */
```
を `:root` に置き、`p` / `.prose` / `.lead` / `.case-body` などの散文ブロックに `max-width: var(--measure)` を当てる。
`table` / `.cards` / `.gallery` / `.hero .facts` は **`--max` のままにする**（表と一覧は広いほうが良い）。

**選択肢にするなら1軸だけ：** `mood` に「行長」を持たせる案もあるが、**推奨しない。** 行長は好みで選ぶものではなく、外していい値がない。**固定すべき。**

### 4-2. 本文の文字サイズを選べるようにするか

**結論：`theme` の軸として足す価値はある。ただし3段階まで。**

理由：`17px` は「60代向け」としては下限寄りで妥当だが、**取材先の社長の目の状態も、調達担当者の年齢層も案件ごとに違う。** 一方、段階を増やすと `theme.ts` の組み合わせ爆発（配色6×書体5×雰囲気3×レイアウト3＝270通り）がさらに増える。**選択肢は、その場で判断できる数に抑えるのが本事業の方針**（取材のその場で選ぶ、と `Palette.note` にある）。

提案する軸 `TEXT_SIZES`（3段階）：

| id | label | note（取材の場での判断材料） | PC本文 | スマホ本文 | 対応する `--measure` |
|---|---|---|---|---|---|
| `futsu` | 標準 | 既定。一般的なBtoBサイトの読みやすさ | 17px | 17px | 720px（約42字） |
| `ookii` | 大きめ | **迷ったらこちら。** 社長ご本人が読む・役員層が読む場合 | 18px | 17px | 760px（約42字） |
| `totemo` | いちばん大きい | 読み手の年齢が高いと分かっているとき | 20px | 18px | 840px（約42字） |

**重要：文字サイズだけを上げてはいけない。** 文字を大きくしたまま本文幅が固定だと、1行の文字数は**減って**、行長は改善する方向に向かう。上表は**どの段階でも1行42字前後に揃う**ように `--measure` を連動させている。**文字サイズと行長は必ずセットで持つこと。**

**別案（併用推奨）：段階を増やすより、`px` を `rem` に変える。**
`html { font-size: 106.25% }`（＝17px）とし、`body { font-size: 1rem }` にすれば、**利用者がブラウザの既定文字サイズを大きくしていれば自動で追従する。** 選択肢を増やさずに、いちばん困っている利用者に届く。**こちらのほうが費用対効果は高い。**

**「文字サイズ変更ボタン」をページに置くか：** 公的機関サイトでよく見る「文字サイズ 小・中・大」のボタン。**推奨しない。** ブラウザのズーム（Ctrl+マウスホイール、スマホのピンチ）で同じことができ、独自実装は JS とレイアウト崩れのリスクを持ち込む。**BtoB製造業のサイトで払う代償に見合わない。**

### 4-3. 罫線の濃さを選べるようにする

`mood` は既に `--line-width`（2px / 1px / 1px）を持っているが、**太さだけで、濃さを持っていない。** 1px の 1.35:1 は薄すぎる。

案：`Palette` に `lineStrong` を足すか、`--line` そのものを 3:1 を満たす濃さに改める。
藍の場合、`#d9dee4`（1.35:1）→ **`#8b95a1` 前後で 3:1 を超える。** 見た目はかなり変わるので、**「表の罫線だけ濃くする」（`th`/`td` にだけ濃い線を使う）のが現実的。** 区切り線は薄いままでよい。

### 4-4. 書体の選択肢の整理

- **`maru`（丸ゴシック）は、現状 macOS/iOS でしか効かない。** 選択肢として残すなら `note` に「**Windows・Android では通常のゴシック体で表示されます**」と明記すべき（theme.ts の方針＝「その代償は画面に書く」に沿う）。あるいは Webフォント版（M PLUS Rounded 1c 等）を用意するか、**選択肢から外す。**
- **`mincho`（本文も明朝）の `note` に、読みやすさの代償を書くべき。** 現在の note「老舗・信頼。創業が古い会社、代表挨拶が主役の会社に」は印象しか書いていない。**「本文が細くなり、年配の方には読みにくくなることがあります。迷うなら『見出しだけ明朝』を」**といった趣旨を足す。
- **Android での明朝フォールバック**を確認し、必要なら `"Noto Serif JP"` をスタックに入れるか、`mincho` の適用を見出しだけに限る。

### 4-5. `noto`（Webフォント）の note を実測値に差し替える

現在：「★どの端末でも同じ見た目になる。ただし表示が少し遅くなり、Googleへの依存が1つ増える」

**「少し遅くなる」は実態を表していない。** 実測は **約 497 KB・26リクエスト**。
提案：「**本文を表示するのに約 500KB を追加で読み込みます（26ファイル）。回線の弱い現場や古い端末では、文字が一度システムのフォントで表示されたあと、切り替わってガタつきます。**」

## 5. 【最優先】現在の実装で推奨を外している箇所

優先度順。上から3つは、**対象読者（60代）に対して実害があると判断した。**

### 1位：本文の1行が 58.8 文字ある（PC表示）

- 場所：`site.css` `:root { --max: 1040px }` ＋ `.inner { padding: 0 20px }`、`p` に `max-width` なし
- 実測：本文幅 1000px ÷ 17px = **58.8 全角文字/行**
- 推奨：35〜45字（通説）／30〜40字（より厳しい説）
- **どの説を採っても 31〜96% 超過。** 60代の読者は行の折り返しで次行の頭を見失いやすい
- 直し方：散文にだけ `--measure: 720px` 前後を当てる。`--max` は触らない
- **根拠の強さの注記：「35〜45字」自体は【検索要約】で、高齢者を対象にした一次研究は取れていない。** ただし**通説の上限をこれだけ超えている**という事実は動かない

### 2位：琥珀パレットが WCAG AA（4.5:1）を4箇所で落としている

- 場所：`theme.ts` `PALETTES` の `kohaku`、`accent: "#b06a10"`
- 実測（白背景 `#fffdfa` に対して）：

| 箇所 | 実測値 | 必要値 |
|---|---|---|
| `a` リンク 17px | **4.21:1** | 4.5:1 |
| 現在地ナビ 15px/600（`accent`/`bg-soft`） | **3.90:1** | 4.5:1 |
| `.btn` の白文字 17px/600 | **4.27:1** | 4.5:1 |
| `.cta` の白文字本文 17px | **4.27:1** | 4.5:1 |

- **17px/600 は「大きなテキスト」に該当しない**（24px 以上、または19px以上の太字が条件）ので、緩和されない
- 参考：`accent` を **`#a5620e`** にすると 4.75:1 / 4.82:1 で AA を通る（見た目の変化はごく小さい）。**`#94580c`** なら 5.65:1 / 5.74:1 で余裕が出る
- さらに **`#b06a10` は黄〜橙系で、加齢による水晶体黄変の影響をいちばん受ける色相。** 数値を直しても色相の不利は残る。`note` の「生活サービス・住宅まわり。硬すぎず、親しみが要るとき」は、**対象読者が60代である本事業の前提と噛み合っていない**

### 3位：表の罫線が 1.22〜1.37:1 しかない（全6パレット）

- 場所：`site.css` `--line`、`th, td { border: var(--line-width) solid var(--line) }`
- 実測：`--line` vs `--bg` = 1.32〜1.37:1、vs `--bg-soft` = 1.22〜1.27:1。**3:1 の半分以下**
- **site.css は冒頭で「写真が1枚も無くても成立すること」「文字と表だけで読める設計」を宣言している。** その表の罫線が 1.35:1 では、設計意図が実装されていない
- 材質表・板厚表・設備一覧は、**調達担当者がいちばん見る部分**
- 形式上は「装飾の境界は 1.4.11 の対象外」と争えるが、**争う意味がない。表の罫線は情報を担っている**

### 4位：`--tap` が未定義で、スマホのメニューボタンの最小高さが効いていない

- 場所：`site.css` 200行目 `min-height: var(--tap)`。`--tap: 44px` は `tool/public/style.css`（管理画面用）にしか無く、`themeVars()` も出力していない
- 結果：計算値として無効 → `min-height: auto` に落ちる
- 実害：現状は padding と line-height でおよそ54pxになり**たまたま**足りているが、**保証がない。** `--leading` や本文サイズを変えると崩れる
- **スマホでサイト内を移動する唯一の入口のボタン**

### 5位：`.tel-label` 11px、その他 13px が5箇所

- 場所：`site.css` `.tel-label { font-size: 11px }`、`.case-industry` / `.case-tags em` / `.copy` / `.price span` が 13px
- 推奨下限（【検索要約】）は 14px、60代向けなら 16px
- **とくに `.tel-label` は電話番号の上のラベル。BtoB中小製造業の問い合わせは電話が主経路**。ここが最小フォントなのは逆行

### 6位：墨・鋼パレットで、リンクが本文と色で区別できない

- 実測：墨 `accent #1d1d1d` vs `ink #141414` — **ほぼ同じ黒。** 鋼 `accent #3d4852` vs `ink #1c1f22` — **色相差ほぼゼロの暗色同士**
- コントラスト比（16.86:1 / 9.34:1）は極めて良好だが、**「読める」と「リンクだと分かる」は別の問題**
- §1-5 の「濃い色同士は区別がつきにくい」に該当
- `site.css` の `a` には `text-decoration` の明示がなく、**ブラウザ既定の下線だけが手がかり**

### 7位：`maru`（丸ゴシック）が Windows / Android で丸ゴシックにならない

- 場所：`theme.ts` `FONTS` の `maru`、スタック `"Hiragino Maru Gothic ProN", "Yu Gothic", system-ui, sans-serif`
- 丸ゴシックは macOS/iOS のみ。Windows は第2候補の **Yu Gothic（通常のゴシック）** に落ちる
- **`theme.ts` 冒頭の「片方だけ増やすと、選べるのに反映されない選択肢ができる」という戒めに、まさに抵触している**
- **【未確認】** 実機での検証はしていない。フォントスタックからの推論

### 8位：`body { font-size: 17px }` が px 固定

- 利用者がブラウザの既定フォントサイズを大きくしていても追従しない（ページズームには追従する）
- `rem` 化すれば、**選択肢を増やさずに**、いちばん困っている利用者に届く

## 補遺：直さなくてよいと判断した箇所

公平を期すために書いておく。

- **`--leading` の 1.75 / 1.85 / 2.0** — 3種とも推奨（1.7〜1.9）の範囲か、その近傍。**妥当。**
- **PC本文 17px** — 推奨（17〜18px）の範囲内。**妥当。** `h2` 24px も「20px以上」を満たす
- **藍・鋼・深緑・臙脂・墨のテキストコントラスト** — 全用途で AA（4.5:1）を満たす。**本文（ink/bg）は 15.92〜18.42:1 で AAA（7:1）も大きく上回る**
- **`gothic` が既定であること** — Web本文の標準はゴシック体、という通説に一致
- **`webfont: null` が既定であること** — 実測 497KB を払わない既定は正しい
- **スマホの表の縦積み**（`table, tbody, tr, th, td { display: block }`）— 横スクロールする表は読まれない、という判断は妥当
- **`-webkit-text-size-adjust: 100%`** — iOS の勝手な文字拡大を止める指定。妥当
- **`.btn { white-space: normal }`（スマホ）** — 妥当
