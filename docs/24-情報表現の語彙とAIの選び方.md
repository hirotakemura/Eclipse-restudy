# 情報表現の語彙と、AIがどう選ぶか — 設計

作成: 2026-09-13 ／ **コードはまだ書いていません**（語彙の測定と設計のみ）。

---

## 0. ご指摘を数字にしました

> 「6種類のデザイン」というより、**「同じ情報構造を持つテンプレートに6種類のビジュアルテーマを適用している」**

`npm run qa:directions` に**2つ目の物差し**を足しました。
1つ目は順番・面・組み方まで見るので、**見た目が違えば下がります。**
2つ目は**出ている情報の種類だけ**を見ます。

| 物差し | 値 | 意味 |
|---|---|---|
| 見た目の似ている度合い | **0.07**（同一 0/15） | 見え方は分かれた |
| **出ている情報の種類の重なり** | **0.76**（**同一 4/15**） | **中身はほぼ同じ** |

```
標準      他社が断った案件／加工事例／どうやって受けているか／対応条件／対応材質
設計・技術  他社が断った案件／加工事例／どうやって受けているか／対応条件／対応材質
   ↑ 種類はまったく同じ。違うのは順番と見た目だけ
```

**ご指摘のとおりでした。**

---

## 1. 原因：「何を出すか」と「どう見せるか」が一体になっている

いまの `Section.kind` は、**内容と表現をひとつの語で表しています。**

| kind | 内容 | 表現 | 変えられるか |
|---|---|---|---|
| `materials` | 対応材質 | **必ず**札（chips） | ✗ |
| `figures` | 条件の数値 | **必ず**横並びの数字 | ✗ |
| `cases` | 加工事例 | **必ず**カードの格子 | ✗ |
| `technique` | 工程の工夫 | **必ず**散文 | ✗ |

だから、型を変えても**同じ内容が同じ形で出ます。**
面や組み方が変わっても、それは「テーマの適用」にしかなりません。

---

## 2. 直し方：内容と表現を分ける

```ts
interface Block {
  content: ContentId;        // 何を出すか（材質・事例・工程・沿革・人・条件…）
  presentation: PresentationId;  // どう見せるか（札／大きな数字／年表／工程図／引用…）
  emphasis; width; surface; layout; media; motif;   // いまもある
}
```

**同じ内容でも、会社によって表現が変わります。**

| 会社の最大の強み | 「対応条件」の見せ方 | 「加工事例」の見せ方 |
|---|---|---|
| 精度 | **大きな数字**（±0.01mm を画面いっぱい） | 仕様表（材質・公差・結果を並べる） |
| 難加工 | 仕様表（条件は脇役） | **課題 → 解決の流れ**（Process） |
| 歴史・職人 | 一覧（控えめ） | **引用**（お客様の言葉を大きく） |
| 短納期・対応力 | **比較**（標準7日 ／ 最短3日） | **工程の流れ**（相談から納品まで） |

## 3. 情報表現の語彙（有限）

**種類を増やすことが目的ではありません。** 安全に組み合わせられる範囲に留めます。

| id | 名前 | 何に向くか | 写真 |
|---|---|---|---|
| `prose` | 散文 | 理由・背景を語る | 不要 |
| `list` | 箇条書き | 数が少なく、並列なもの | 不要 |
| `chips` | 札 | 検索される語（材質・加工法） | 不要 |
| `cardGrid` | カードの格子 | 件数があり、各件が独立している | あると良い |
| `largeNumber` | 大きな数字 | **1〜3個の強い数値**。埋もれさせない | 不要 |
| `spec` | 仕様表 | 項目が多く、突き合わせて読む | 不要 |
| `comparison` | 対比 | **2つの値を並べて見せる**（標準 ／ 最短） | 不要 |
| `timeline` | 年表 | 時系列。**3件以上ないと作らない** | 不要 |
| `process` | 工程の流れ | 順序に意味がある（相談→図面→加工→検査） | 不要 |
| `quote` | 引用 | **人の言葉をそのまま大きく** | 不要 |
| `editorial` | 読み物 | 長い文章を読ませる | 不要 |
| `fullWidth` | 全幅 | 写真・図を画面いっぱいに | **要** |

**12個。これ以上は増やしません。**

### ファーストビュー（ご指示の6つに合わせる）

| ご指示 | うちの名前 | いまの実装 |
|---|---|---|
| Oversized Typography | 余白と文字だけ | `type` ○ |
| Large Numeric | 数字を大きく | `figure` ○ |
| Split | 左右2分割 | **新設** |
| Editorial | 読み物 | **新設** |
| Technical | 技術の地紋 | `motif` ○ |
| Statement | 言い切り | `headline`（改名） |

**写真は独立した型にしません。** `media` が決めます。
写真の有無でファーストビューの「形」まで変わってしまうと、
**写真が揃った瞬間にサイトの骨格が変わる**ことになり、お客様に説明できません。

## 4. 「この内容にこの表現は使えるか」を型で縛る

**これが安全装置です。** AIが選べるのは、この表の○だけ。

| 内容 ＼ 表現 | prose | list | chips | cardGrid | largeNumber | spec | comparison | timeline | process | quote | editorial |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 対応条件 | | ○ | | | ○ | ○ | ○ | | | | |
| 対応材質 | | ○ | ○ | | | ○ | | | | | |
| 設備 | | ○ | | ○ | ○ | ○ | | | | | |
| 加工事例 | | | | ○ | | ○ | | | ○ | ○ | |
| 工程の工夫 | ○ | ○ | | | | | | | ○ | | ○ |
| 他社が断った案件 | ○ | | | | | | | | | ○ | ○ |
| お客様の言葉 | ○ | | | ○ | | | | | | ○ | |
| 沿革 | ○ | ○ | | | | | | ○ | | | ○ |
| 代表 | ○ | | | | | | | | | ○ | ○ |

さらに**材料の条件**を持たせます。

- `largeNumber` … 短く言い切れる値があること（D-203で入れた判定）
- `timeline` … 3件以上
- `comparison` … 2つの値が取れること
- `process` … 順序のある記述があること
- `quote` … 鍵括弧つきの発言が取れていること
- `cardGrid` … 2件以上
- `fullWidth` … 実写があること

**表に○があっても、材料が無ければ選べません。**

## 5. Company Analysis を「最大の強み」まで出す形にする

いまの `analyze()` は8つの見立てを点数で返すだけです。
ご指示の4例に対応するため、**1位を「何で選ばれている会社か」として名前を付けます。**

```ts
type PrimaryStrength =
  | "precision"   // 精度が最大の強み
  | "difficulty"  // 難加工が最大の強み
  | "heritage"    // 歴史・職人性が最大の強み
  | "response"    // 短納期・対応力が最大の強み
  | "equipment"   // 設備・量産能力
  | "product";    // 製品・開発力
```

判定は**いまの見立ての点数から機械的に**出します（D-181：規則で決められるものに生成を挟まない）。

| 最大の強み | 主役にする内容 | 主役の表現 |
|---|---|---|
| 精度 | 対応条件 | `largeNumber` |
| 難加工 | 加工事例 | `process`（課題→解決） |
| 歴史・職人 | 沿革・代表 | `timeline` ＋ `quote` |
| 短納期・対応力 | 対応条件 | `comparison`（標準／最短） |
| 設備・量産 | 設備 | `cardGrid` ＋ `largeNumber`（台数） |
| 製品・開発 | 加工事例 | `editorial` |

## 6. Content Journey は骨格として残す

ご指示どおり、**順序の決定者は1つ**にします。

```
骨格（全社共通・変えない）
  1. この会社の第一印象
  2. 何ができる会社か
  3. その根拠（技術・実績）
  4. 判断材料（条件・設備）
  5. 問い合わせ

   ↓ この骨格の中で、Company Analysis が変えるもの

  ・各段に何を入れるか（内容の選択）
  ・その表現（12の語彙から）
  ・情報量（何件出すか）
  ・大きさ（lead / normal / quiet）
  ・面・組み方・地紋
  ・カードにするか、しないか
```

**骨格が同じでも、中身と表現が変われば別のサイトになります。**
骨格まで会社ごとに変えると、**商談で説明できなくなり、検査もできません。**

## 7. AIがどう選ぶか

### 入力と出力

```
入力： Company Analysis（事実）＋ Direction（型の好み）＋ Journey（骨格）
       ＋ **語彙表と可否表**（第3・4章）
出力： Design Brief（**enum の値だけ**の JSON）
```

```json
{
  "primaryStrength": "difficulty",
  "hero": { "form": "statement", "media": "none" },
  "blocks": [
    { "content": "declined",  "presentation": "quote",    "emphasis": "lead" },
    { "content": "cases",     "presentation": "process",  "emphasis": "normal" },
    { "content": "technique", "presentation": "editorial","emphasis": "normal" },
    { "content": "conditions","presentation": "spec",     "emphasis": "quiet" }
  ],
  "motif": "section",
  "motionLevel": "subtle"
}
```

**文章も数値も作らせません。** 値はすべて語彙のIDです（D-200）。

### 4段の検査

1. **形** … JSON として読めるか。知らないキーが無いか
2. **語彙** … すべての値が語彙表にあるか
3. **可否** … 内容 × 表現の組み合わせが表の○か
4. **材料** … その表現に必要なデータが実際にあるか

**どれか1つでも落ちたら、規則版の Brief に落とす。**
AIが落ちても生成は止まりません。**止まらないことが要件です。**

### なぜAIを使うのか（使わない案との比較）

規則だけでも、第5章の表があれば動きます。実際、**段階3までは規則だけでやってきました。**

AIに任せたいのは、**表に落とし切れない判断**です。

- 「難加工が強みだが、事例が1件しかない」→ 事例を主役にしてよいか
- 「精度が強みだが、値が未確認」→ 何を代わりに主役にするか
- 「歴史も技術も強い」→ どちらを先に置くか

**規則で書けるものは規則のまま**にして、AIには**この種の判断だけ**を任せます。
判断の理由も一緒に返させ、書き出しのときに表示します（D-184）。

### 費用

1案件につき1回の呼び出し。前回お答えしたとおり**増分は「1ページ分」程度**です。
語彙のIDしか返さないので、出力は短くなります。

## 8. 検査（ご指示⑥の3段に当てはめる）

| 段 | 足すもの |
|---|---|
| 1. 機械検査 | Brief の4段検査（形・語彙・可否・材料）。**AIの出力を必ず通す** |
| 2. Design System 検査 | 語彙の外の表現が使われていないか。`opacity:0` の焼き込み |
| 3. Visual QA | `qa:directions` の**2つの物差し**。加えて**同じ型で会社を変えた比較**（今回の逆） |

### 合格の基準

```
いま      見た目 0.07（同一 0/15）／ **情報の種類 0.76（同一 4/15）**
目標      見た目 0.10 以下         ／ **情報の種類 0.40 以下（同一 0/15）**
```

**見た目の数字は下げすぎないこと。** 下げるために奇抜にしては本末転倒です（ご指示⑲）。
**動かしたいのは2つ目の数字**です。

さらに、**同じ会社・同じ型で、聞き取りだけを変えた比較**も要ります。
「精度が強い会社」「難加工が強い会社」を作って、**同じ型でも違う表現になる**ことを確かめます。

---

## 9. 進め方

1. `Block` を `content` ＋ `presentation` に分ける（**出力は変えない。既定の表現を今と同じにする**）
2. 表現の語彙12個と可否表を定義し、検査を書く
3. Company Analysis に「最大の強み」を足す
4. 規則版で、最大の強みに応じて表現を変える → **測る**
5. AI版の Brief（語彙から選ばせる・4段検査・規則版へ落とす）
6. 同じ型・違う会社での比較を Visual QA に足す

**1と2は出力が変わりません。** 変わるのは4からです。

# 追加の取り決め（2026-09-13・アドバイザー指示を反映）

## ★ 最重要の設計思想

> **この改修の目的は「情報の種類を減らして違いを作る」ことではない。**
>
> **「同じ必要情報を持っていても、その会社にとって何が重要なのかによって、
> 情報の見せ方が変わる」状態を作ること。**

以下の取り決めは、すべてこの一文から導かれる。

---

## 1. 「情報の種類の重なり 0.40以下」は目標ではなく警告値（D-204）

**0.40 という数値を、生成ルールの目的にしない。**

製造業のサイトでは、**重要な情報が共通するのは当然**である。
次の情報は、SEOと営業の両方で効くので、**必要なら何社でも共通して出してよい。**

```
対応可能範囲 ／ 対応材質 ／ 対応条件 ／ 設備 ／ 加工事例 ／ 技術情報 ／ お問い合わせ
```

**「他社と同じ情報だから削る」という判断は、絶対にしない。**

差を作る対象は、削ることではなく：

```
重要度 ／ 順番 ／ presentation ／ 情報量 ／ 大きさ ／ 背景 ／ レイアウト
```

数値は **Visual QA で「多様性が出ているか」を見るための警告値**として使う。
下がらないときに疑うのはルールであって、**情報を削る理由にはしない。**

---

## 2. `primaryStrength` を推測で決めない（D-205）

**根拠となる聞き取りがあるときだけ設定する。**

| 値 | 根拠として要るもの |
|---|---|
| `precision` 精度 | `capability.tolerance` |
| `difficulty` 難加工 | `strengths.wonAfterOthersDeclined` または `workOthersAvoid` |
| `response` 短納期・対応力 | `capability.shortestLeadTime` ＋ `lotSize` |
| `coverage` 対応範囲 | `capability.materials` 3件以上 ＋ `processes` |
| `design` 設計対応 | `strengths.followUpFindings`（設計・図面の記述） |
| `equipment` 設備 | メーカー・型番の揃った設備が1台以上 |
| `craft` 職人性 | `strengths.followUpFindings` ＋ `praiseFromClients` |
| `heritage` 歴史 | `basics.founded` ＋ `history` 3件以上 |
| **`unknown`** | **上のどれにも当てはまらない** |

> **AIが「この会社は精度が強みだろう」と推測してはいけない。**
>
> 製造業で「精度が強み」と勝手に判断されると、**事実確認の思想と正面から衝突する。**
> 公差を聞き取れていないのに精度で売る構成にすることは、嘘をつくのと同じである。
>
> `unknown` のときは、**規則版の安全な構成へ落とす。**

---

## 3. content と presentation の責務（D-206）

```
content       = 何を伝えるか
presentation  = どう見せるか
```

**この2つを混ぜない。** 例：

```
{ content: "materials", presentation: "chips" }   ○ 許可
{ content: "materials", presentation: "spec" }    ○ 許可
{ content: "materials", presentation: "timeline" } ✗ 可否表で禁止
```

**AIに「自由にデザインさせる」のではない。** 順序を固定する：

```
Company Analysis
   ↓
適切な content を選ぶ
   ↓
適切な presentation を選ぶ
   ↓
可否表（content × presentation）
   ↓
材料の存在・条件の確認
   ↓
生成
```

---

## 4. 「散文」と「読み物」を混ぜない／カードは禁止ではない（D-207）

| id | 名前 | 定義 | 実装上の違い |
|---|---|---|---|
| `prose` | 散文 | **短い説明・通常の本文。** 数行で用が足りるもの | 幅は `--measure`（40em前後）。見出しは h3 まで |
| `longform` | 読み物 | **長めの文章を、余白・段落・引用で読ませる。** 読ませることが目的 | 段落の間隔を広く、書き出しを大きく、引用を挟む。帯の余白も広い |

> **ご指示の「Editorial」はこの `longform` にあたる。**
> `editorial` という名前は**組み方（layout）の側ですでに使っている**ので、
> 表現の側は `longform` とする。**同じ名前を2つの軸で使わない。**

**`cardGrid` は禁止ではない。「既定にしない」** だけである。

- 件数があり、各件が独立して読まれるもの（加工事例・設備）には**適切**
- 「情報だからカードに入れる」という判断だけを禁止する

---

## 5. 4段検査の順序（D-208）

```
1. 形      JSONとして読めるか。知らないキーが無いか
2. 語彙    すべての値が語彙表にあるか
3. 可否    content × presentation が可否表の○か
4. 材料    その表現に必要なデータが実際にあるか
```

**どこで落ちても、生成は止めない。規則版へ落とす。**

---

## 6. 検証は2方向。**②を重視する**（D-209）

| | 何を確かめるか | いまの状態 |
|---|---|---|
| ① 同じ会社 × 違う型 | 6方向で見た目・表現が変わるか | `npm run qa:directions`（実装済み） |
| **② 同じ型 × 違う会社** | **Company Analysis で情報表現が変わるか** | **未実装。今回いちばん重要** |

②の具体例（同じ「精密加工」でも）：

```
A社：精度が強み    → 大きな数値・仕様表現
B社：難加工が強み  → 課題→解決・加工プロセス
C社：短納期が強み  → 標準納期／最短納期・工程表現
```

**これが成立すれば、「6種類のテンプレート」から
「Design Direction × Company Analysis × Presentation Vocabulary」へ移行できたと判断する。**

## 7. 1・2の実装では、既存の出力を変えない（D-210）

1歩目と2歩目で実装するのは：

- `Block` の構造変更（`content` ＋ `presentation`）
- presentation の語彙・可否表・検査

**この段階で既存案件の見え方を意図的に変えない。**
いまの `kind` は `(content, presentation)` の組として読み替えるだけにする。

変わるのは4歩目からである。
